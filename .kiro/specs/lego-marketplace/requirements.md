# GoLe LEGO Marketplace — Requirements

> 형식: EARS (Easy Approach to Requirements Syntax). `~할 때(WHEN) / ~하면(IF) / 항상(SHALL)` 패턴으로 검증 가능한 단일 행위를 기술한다.
> 본 문서는 현재 구현(`apps/api`, `apps/web`)을 정식 스펙으로 역정규화하여, 향후 변경의 단일 기준이 된다.

## 0. 개요

GoLe는 레고 중고거래 플랫폼이다. 체결가 기반 시세·안전거래, 동네 직거래, 보유/희망 컬렉션, 셀러 샵·팔로우를 한곳에서 제공한다.

| 영역 | 바운디드 컨텍스트 | 책임 |
|---|---|---|
| 1 | **account** | 회원가입, 이메일 인증, 로그인(세션), 권한(RBAC) |
| 2 | **catalog** | 레고 세트 카탈로그(검색/추천/조회) |
| 3 | **listing** | 중고 매물 등록/검색/상태관리 |
| 4 | **order** | 안전거래 주문 라이프사이클(에스크로) |
| 5 | **pricing** | 체결가 기반 시세 통계/차트/이력 |
| 6 | **collection** | 사용자 보유/희망 컬렉션 및 추정가 |
| 7 | **community** | 자랑/MOC 피드, 댓글, 좋아요 |
| 8 | **discovery** | 셀러 샵, 팔로우, 위시리스트, 개인화 피드 |
| 9 | **review** | 거래 후기 및 셀러 평점 |
| 10 | **admin** | 운영 대시보드 및 카탈로그 관리(ADMIN 전용) |

### 공통 비기능 요구사항 (NFR)

- NFR-1: 시스템은 모든 도메인 오류를 `{ "code": string, "message": string }` 형태의 JSON과 적절한 HTTP 상태코드로 응답해야 한다(SHALL).
- NFR-2: 모든 API 경로는 `/api/v1/...` 프리픽스를 사용해야 한다(관리자 API는 `/api/admin`).
- NFR-3: 백엔드는 헥사고날 아키텍처(domain → application(port in/out) → adapter)를 준수해야 하며, 컨텍스트 간 연동은 다른 컨텍스트의 인바운드 포트(UseCase)에만 의존해야 한다.
- NFR-4: 프론트엔드는 FSD 레이어 의존 규칙(app→views→widgets→features→entities→shared, 단방향)을 위반하지 않아야 한다.
- NFR-5: 금액은 정수 최소단위(KRW, long)로 저장/계산해야 하며 부동소수점을 사용하지 않아야 한다.
- NFR-6: 멀티 도큐먼트 일관성이 필요한 유스케이스는 MongoDB 트랜잭션(replica set rs0)을 사용해야 한다.

## 요구사항 1 — 계정 / 인증 (account)

**사용자 스토리:** 사용자로서, 이메일로 가입하고 인증한 뒤 로그인하여 거래 기능을 이용하고 싶다.

#### 수용 기준
- 1.1 WHEN 사용자가 이메일·비밀번호로 회원가입을 요청하면, 시스템은 계정을 `UNVERIFIED` 상태·`USER` 권한으로 생성하고 인증코드를 발급해야 한다.
- 1.2 IF 이미 등록된 이메일로 가입을 요청하면, 시스템은 409 `EMAIL_ALREADY_REGISTERED`로 거부해야 한다.
- 1.3 IF 비밀번호가 정책(최소 강도)을 만족하지 않으면, 시스템은 가입을 `WEAK_PASSWORD`로 거부해야 한다.
- 1.4 WHEN 올바른 인증코드를 제출하면, 시스템은 계정을 `VERIFIED`로 전이하고 인증코드를 제거해야 한다.
- 1.5 IF 인증코드가 만료되었으면, 시스템은 `VERIFICATION_CODE_EXPIRED`로 거부해야 한다.
- 1.6 IF 인증코드가 일치하지 않으면, 시스템은 `VERIFICATION_CODE_MISMATCH`로 거부해야 한다.
- 1.7 WHEN 이미 인증된 계정이 다시 인증을 시도하면, 시스템은 멱등하게 성공 처리해야 한다.
- 1.8 IF 로그인이 15분 창 내에 5회 실패하면, 시스템은 해당 계정을 15분간 잠그고(`ACCOUNT_LOCKED`) 그 동안의 로그인을 거부해야 한다.
- 1.9 WHEN 로그인에 성공하면, 시스템은 실패 카운터/잠금을 초기화하고 불투명(opaque) 세션 토큰과 권한(role)을 반환해야 한다.
- 1.10 IF 자격증명이 틀리면, 시스템은 401 `INVALID_CREDENTIALS`로 거부해야 한다.
- 1.11 WHEN `Authorization: Bearer <token>`으로 `/me`를 호출하면, 시스템은 세션을 해석해 accountId·role을 반환하고, 유효하지 않으면 401 `INVALID_SESSION`을 반환해야 한다.
- 1.12 시스템은 비밀번호를 BCrypt(자동 솔트)로 저장해야 하며, 레거시(SHA-256) 해시로 저장된 기존 계정은 로그인 성공 시 동일 비밀번호를 BCrypt로 재해시·교체(점진 마이그레이션)해야 한다. 이 과정에서 기존 사용자의 로그인은 중단되지 않아야 한다.

## 요구사항 2 — 카탈로그 (catalog)

**사용자 스토리:** 사용자로서, 레고 세트를 검색·열람하여 거래/시세의 기준 정보를 얻고 싶다.

#### 수용 기준
- 2.1 WHEN 추천 세트를 요청하면, 시스템은 `featured` 플래그가 설정된 세트 목록을 반환해야 한다.
- 2.2 WHEN 세트번호로 조회하면, 시스템은 해당 세트를 반환하고, 없으면 404 `LEGO_SET_NOT_FOUND`를 반환해야 한다.
- 2.3 WHEN 검색어로 조회하면, 시스템은 이름/세트번호/테마에 매칭되는 세트 목록을 반환해야 한다.
- 2.4 세트는 setNumber, name, theme, pieceCount, releaseYear, retirementStatus(`ACTIVE`/`RETIRED`), imageUrl, featured 속성을 가져야 한다.

## 요구사항 3 — 매물 등록/관리 (listing)

**사용자 스토리:** 셀러로서, 보유 레고를 사진·상태와 함께 등록하고 판매 상태를 관리하고 싶다.

#### 수용 기준
- 3.1 WHEN 셀러가 매물을 등록하면, 시스템은 매물을 `ACTIVE` 상태로 생성해야 한다.
- 3.2 IF 사진(photoUrls)이 하나도 없으면, 시스템은 등록을 `MISSING_PHOTO`로 거부해야 한다.
- 3.3 매물은 컨디션(`NEW_SEALED`/`USED_COMPLETE`/`USED_INCOMPLETE`)과 구성 고지(완전성 `FULL_BOX`/`NO_BOX`/`BULK`, 박스/설명서/누락부품 여부, 누락·하자 메모)를 포함해야 한다.
- 3.4 IF 가격이 양수가 아니면, 시스템은 `INVALID_PRICE`로 거부해야 한다.
- 3.5 WHEN 매물 검색을 요청하면, 시스템은 키워드/컨디션/최소·최대가/정렬(`sort`) 필터를 적용해 `ACTIVE` 매물만 반환해야 하며, 파라미터가 없으면 최신순 전체를 반환해야 한다.
- 3.6 WHEN 매물을 ID로 조회하면, 시스템은 해당 매물을 반환하고 없으면 404 `LISTING_NOT_FOUND`를 반환해야 한다.
- 3.7 WHEN 셀러가 판매완료 처리하면, 시스템은 매물을 `SOLD`로 전이해야 한다(단, `DELETED`면 거부).
- 3.8 IF 매물에 진행 중 주문이 있어 `RESERVED` 상태이면, 시스템은 삭제를 `LISTING_ORDER_IN_PROGRESS`로 거부해야 한다.
- 3.9 WHEN 삭제가 허용되면, 시스템은 매물을 `DELETED`로 전이해야 한다.

## 요구사항 4 — 안전거래 주문 (order)

**사용자 스토리:** 구매자로서, 에스크로(자금 보유) 기반 안전거래로 매물을 구매하고 싶다.

#### 수용 기준
- 4.1 WHEN 구매자가 `ACTIVE` 매물에 주문을 생성하면, 시스템은 주문을 `PAYMENT_PENDING`으로 만들고 매물을 `RESERVED`로 선점해야 한다.
- 4.2 IF 매물이 활성 상태가 아니면, 시스템은 주문 생성을 `ITEM_UNAVAILABLE`로 거부해야 한다.
- 4.3 WHEN 결제가 승인되면, 시스템은 주문을 `FUNDS_HELD`로 전이해야 한다.
- 4.4 IF 결제가 실패하면, 시스템은 주문을 `PAYMENT_FAILED`로 전이하고 매물 선점을 해제(`ACTIVE` 복귀)해야 한다.
- 4.5 WHEN 구매자가 구매확정하면, 시스템은 `FUNDS_HELD` 주문을 `COMPLETED`로 전이하고 셀러 정산을 트리거하며 매물을 `SOLD`로 처리해야 한다.
- 4.6 WHEN `FUNDS_HELD` 주문에 환불을 요청하면, 시스템은 주문을 `REFUNDED`로 전이하고 매물 선점을 해제해야 한다.
- 4.7 IF 현재 상태에서 허용되지 않는 전이를 요청하면, 시스템은 `ORDER_STATE`(409)로 거부해야 한다.
- 4.8 주문은 모든 상태 전이 이력(상태, 시각)을 보존해야 한다.
- 4.9 동시 결제/주문 시 시스템은 낙관적 락(`@Version`)으로 이중 판매를 방지해야 한다.

## 요구사항 5 — 시세 (pricing)

**사용자 스토리:** 사용자로서, 특정 세트의 실거래가 추이를 확인하고 합리적 가격을 판단하고 싶다.

#### 수용 기준
- 5.1 WHEN 주문이 `COMPLETED`되면, 시스템은 체결가(setNumber, amount, 시각)를 시세 이력에 기록해야 한다.
- 5.2 WHEN 세트의 통계를 요청하면, 시스템은 기간(from/to) 내 최소/최대/평균/중앙값/거래건수를 반환해야 하며, 데이터가 없으면 `noData` 형태를 반환해야 한다.
- 5.3 WHEN 차트를 요청하면, 시스템은 기간 내 시계열 가격 포인트를 반환해야 한다.
- 5.4 WHEN 이력을 요청하면, 시스템은 해당 세트의 전체 체결 이력을 반환해야 한다.

## 요구사항 6 — 컬렉션 (collection)

**사용자 스토리:** 컬렉터로서, 보유/희망 세트를 기록하고 컬렉션의 추정 가치를 보고 싶다.

#### 수용 기준
- 6.1 WHEN 사용자가 세트를 컬렉션에 추가하면, 시스템은 상태(`OWNED`/`WANTED`/`SOLD`)와 함께 항목을 저장해야 한다.
- 6.2 WHEN 사용자의 컬렉션을 조회하면, 시스템은 해당 사용자의 모든 항목을 반환해야 한다.
- 6.3 WHEN 항목 삭제를 요청하면, 시스템은 소유자(userId) 검증 후 항목을 제거하고, 소유자가 아니면 거부해야 한다.
- 6.4 IF 컬렉션 항목이 없으면, 시스템은 삭제 요청에 404 `COLLECTION_ITEM_NOT_FOUND`를 반환해야 한다.
- 6.5 WHEN 추정가를 요청하면, 시스템은 `OWNED` 항목들의 최신 시세 합산값을 반환해야 한다.

## 요구사항 7 — 커뮤니티 (community)

**사용자 스토리:** 사용자로서, 조립/MOC를 자랑하고 다른 사용자와 댓글·좋아요로 교류하고 싶다.

#### 수용 기준
- 7.1 WHEN 사용자가 게시글을 작성하면, 시스템은 글을 `PUBLISHED`로 생성해야 한다(타입 `GENERAL`/`MOC`).
- 7.2 IF 게시글에 이미지가 하나도 없으면, 시스템은 작성을 `POST_IMAGE_REQUIRED`로 거부해야 한다.
- 7.3 WHEN 피드를 요청하면, 시스템은 게시글 목록을 반환해야 한다.
- 7.4 WHEN 게시글을 좋아요하면, 시스템은 좋아요를 1회만 반영하고 중복 시 `DUPLICATE_LIKE`로 거부해야 한다.
- 7.5 WHEN 댓글을 작성/조회하면, 시스템은 해당 게시글의 댓글을 저장/반환해야 한다.
- 7.6 WHEN 작성자가 자신의 글 삭제를 요청하면, 시스템은 글을 삭제(`DELETED`)해야 하며, 작성자가 아니면 거부해야 한다.
- 7.7 IF 존재하지 않는 게시글을 조회하면, 시스템은 404 `POST_NOT_FOUND`를 반환해야 한다.

## 요구사항 8 — 디스커버리 (discovery)

**사용자 스토리:** 사용자로서, 마음에 드는 셀러를 팔로우하고 위시리스트를 모아 개인화된 매물 피드를 받고 싶다.

#### 수용 기준
- 8.1 WHEN 셀러 샵을 조회하면, 시스템은 해당 셀러의 매물 요약 목록을 반환해야 한다.
- 8.2 WHEN 사용자가 셀러를 팔로우하면, 시스템은 팔로우 관계를 저장하고 중복 시 `DUPLICATE_FOLLOW`로 거부해야 한다.
- 8.3 WHEN 언팔로우하면, 시스템은 팔로우 관계를 제거해야 한다(멱등).
- 8.4 WHEN 팔로잉 목록을 조회하면, 시스템은 사용자가 팔로우한 셀러 ID 목록을 반환해야 한다.
- 8.5 WHEN 개인화 피드를 요청하면, 시스템은 사용자가 팔로우한 셀러들의 매물을 반환해야 한다.
- 8.6 WHEN 위시리스트에 항목(`LISTING`/`CATALOG_SET`)을 추가하면, 시스템은 항목을 저장하고 중복 시 `DUPLICATE_WISHLIST`로 거부해야 한다.
- 8.7 WHEN 위시리스트 항목을 삭제/조회하면, 시스템은 해당 동작을 수행/반환해야 한다.

## 요구사항 9 — 거래 후기 (review)

**사용자 스토리:** 구매자로서, 완료된 거래에 후기·평점을 남기고, 셀러의 누적 평점을 확인하고 싶다.

#### 수용 기준
- 9.1 WHEN 구매자가 완료된 주문에 후기를 작성하면, 시스템은 평점(rating)·내용과 함께 후기를 저장해야 한다.
- 9.2 IF 완료되지 않은 주문이거나 작성 권한이 없으면, 시스템은 후기 작성을 거부해야 한다.
- 9.3 WHEN 셀러의 후기 목록을 조회하면, 시스템은 해당 셀러가 받은 후기 목록을 반환해야 한다.
- 9.4 WHEN 셀러의 평점을 조회하면, 시스템은 평균 평점과 후기 수를 반환해야 한다.

## 요구사항 10 — 운영자 (admin)

**사용자 스토리:** 운영자로서, 플랫폼 현황을 집계로 보고 카탈로그 세트를 관리하고 싶다.

#### 수용 기준
- 10.1 IF 요청자가 ADMIN 권한이 아니면, 시스템은 `/api/admin/**`의 모든 요청을 거부해야 한다(AdminAuthInterceptor).
- 10.2 WHEN 운영자가 대시보드 개요를 요청하면, 시스템은 주요 컬렉션별 도큐먼트 수 집계를 반환해야 한다.
- 10.3 WHEN 운영자가 카탈로그 세트 목록을 요청하면, 시스템은 전체 세트를 반환해야 한다.
- 10.4 WHEN 운영자가 세트를 생성하면, 시스템은 세트를 카탈로그에 추가해야 한다.

## 추적성 (Traceability)
