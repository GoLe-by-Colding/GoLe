# 배송 추적 기반 거래 보호 · 수수료 (Shipping & Fees) — 요구사항

## 개요

거래 모델을 **"자유로운 유저 간 채팅 + 송장 추적으로 배송 사실 확인 + 그 위에서만 신고/분쟁 처리
+ 플랫폼 수수료 징수"** 로 정한다. 당근마켓·후르츠패밀리형 구조다.

핵심 전환: 플랫폼이 상품을 검수하거나 물류를 대행하지 않는다. 대신 **택배사 송장 조회 API로
"보냈다/도착했다"는 객관적 사실만 확보**하고, 이 사실을 기준으로 정산 시점과 분쟁 판정을 결정한다.

## 현재 상태 (실측 기준선)

이미 있는 것:
- `OrderStatus`: `PAYMENT_PENDING → FUNDS_HELD → COMPLETED`, `PAYMENT_FAILED`, `REFUNDED`
- `Settlement.compute()` — **플랫폼 수수료율 5% 하드코딩**(`PLATFORM_FEE_RATE = 0.05`)
- `SettlementPort` + `StubSettlementAdapter`(로그만 남김 — 실제 송금 없음)
- `PaymentGatewayPort` + 포트원 어댑터(결제·검증) / 스텁
- `chat` 컨텍스트(유저 간 대화), `report` 컨텍스트(신고)

없는 것:
- 배송/송장 개념 자체가 **전혀 없다**. `Order`에 운송장번호·택배사 필드가 없다.
- `COMPLETED` 전이 조건이 배송 사실과 무관하다(구매자가 누르면 끝).
- 수수료가 도메인 상수 1개로 고정 — 요율 변경·면제·정책 이력이 불가능하다.

## 용어

| 용어 | 의미 |
|---|---|
| 운송장(waybill) | 택배사 + 송장번호 조합. 배송 1건의 식별자 |
| 트래커 | 택배사 배송 상태를 조회하는 외부 API |
| 배송 확정 | 트래커가 `DELIVERED`를 반환한 상태 |
| 자동 구매확정 | 배송 확정 후 일정 기간 무분쟁 시 자동으로 거래를 완료 처리 |
| 수수료(fee) | 거래 성사 시 플랫폼이 취하는 금액 |

## 요구사항

### R1. 운송장 등록

- **R1.1** 판매자는 `FUNDS_HELD` 상태의 주문에 **택배사 + 송장번호**를 등록할 수 있어야 한다.
- **R1.2** 주문의 판매자가 아닌 사용자의 등록 요청은 거부해야 한다(403).
- **R1.3** 송장번호는 숫자·하이픈만 허용하고 공백을 제거해 정규화해야 한다.
- **R1.4** 동일 주문에 운송장을 재등록하면 **직전 값을 대체**하고 변경 이력을 남겨야 한다
  (오등록 정정 허용, 단 흔적은 보존).
- **R1.5** 운송장이 등록되면 구매자에게 알림을 보내야 한다(`notification` 컨텍스트 재사용).

### R2. 배송 상태 추적

- **R2.1** 시스템은 등록된 운송장의 배송 상태를 외부 트래커로 조회해야 한다.
- **R2.2** 배송 상태는 `PENDING`(미접수) / `IN_TRANSIT`(이동중) / `DELIVERED`(배송완료) /
  `UNKNOWN`(조회불가)으로 정규화해야 한다. 택배사별 원문 상태는 그대로 보존한다.
- **R2.3** 트래커 조회는 주기적으로 갱신해야 하며, 조회 실패가 주문 흐름을 막아서는 안 된다
  (graceful degradation — `UNKNOWN`으로 취급).
- **R2.4** `DELIVERED`로 전이하면 배송완료 시각을 기록하고 구매자·판매자에게 알림을 보내야 한다.
- **R2.5** 트래커 응답은 짧은 TTL로 캐시해 외부 API 호출량을 제한해야 한다
  (`trending-sets`의 Redis 캐시 어댑터 패턴 재사용).

### R3. 배송 사실에 근거한 거래 완료

- **R3.1** 구매자는 언제든 수동으로 구매확정(`COMPLETED`)할 수 있어야 한다(기존 동작 유지).
- **R3.2** 배송이 `DELIVERED`가 된 후 **N일**(기본 7일) 동안 분쟁이 없으면
  시스템이 **자동 구매확정**해야 한다.
- **R3.3** 자동 구매확정은 멱등해야 한다. 이미 `COMPLETED`/`REFUNDED`면 아무것도 하지 않는다.
- **R3.4** 운송장이 등록되지 않았거나 `DELIVERED`가 아니면 자동 구매확정을 하지 않는다.

### R4. 신고 · 분쟁

- **R4.1** 구매자는 `FUNDS_HELD` 주문에 대해 분쟁을 제기할 수 있어야 한다
  (미발송 / 미도착 / 상품 불일치 / 파손).
- **R4.2** 분쟁이 열리면 자동 구매확정 타이머를 **정지**해야 한다.
- **R4.3** 분쟁 판정 시 시스템은 **트래커의 객관적 배송 사실을 근거로 제시**해야 한다.
  운영자가 최종 판단하되, 화면에 배송 상태·발송시각·도착시각이 함께 보여야 한다.
- **R4.4** 판정 결과는 환불(`REFUNDED`) 또는 거래 완료(`COMPLETED`) 중 하나여야 한다.
- **R4.5** 미발송 상태(`PENDING`)로 일정 기간이 지나면 구매자가 **일방 환불**을 요청할 수 있어야 한다.

### R5. 수수료

- **R5.1** 수수료율은 **설정으로 외부화**해야 한다. 현재 하드코딩된
  `Settlement.PLATFORM_FEE_RATE = 0.05`를 대체한다.
- **R5.2** 수수료는 **거래 완료 시점에 확정**하고, 계산에 쓰인 요율을 정산 레코드에 함께 저장해야 한다
  (나중에 요율이 바뀌어도 과거 정산을 재현할 수 있어야 한다).
- **R5.3** 최소 수수료와 최대 수수료(상한)를 설정할 수 있어야 한다.
- **R5.4** 수수료는 원 단위 정수로 반올림하고, `payout = gross - fee`가 항상 성립해야 한다.
- **R5.5** 환불된 주문은 수수료를 징수하지 않아야 한다.
- **R5.6** 관리자는 수수료 총액·건수를 조회할 수 있어야 한다(`admin` 컨텍스트).
- **R5.7** 판매자는 매물 등록 전에 현재 요율·하한·상한과 입력 가격 기준 예상 수수료·정산액을
  확인할 수 있어야 한다. 정책 조회 실패 시 임의 요율을 표시하지 않고 등록 기능은 유지한다.

### R7. 자동 파이프라인 (무개입 원칙)

플랫폼 운영의 기본 방침: **정상 거래는 운영자가 아무것도 하지 않아도 끝까지 흘러가야 한다.**
운영자는 예외 건만 본다. 이 원칙이 아래 요구사항의 상위 제약이다.

- **R7.1** 결제 승인부터 정산까지 정상 경로(happy path)에는 **운영자 개입 지점이 0개**여야 한다.
  결제 확정·배송 상태 갱신·구매확정·수수료 확정·정산은 모두 자동으로 일어난다.
- **R7.2** **모든 상태는 타임아웃과 기본 처리(default resolution)를 가져야 한다.**
  어떤 주문도 사람이 안 보면 영원히 멈춰 있는 상태에 빠지면 안 된다.
- **R7.3** 자동 전이는 전부 **멱등**해야 한다. 스케줄러가 중복 실행되거나 재시작돼도
  이중 정산·이중 알림이 발생하지 않아야 한다.
- **R7.4** 자동 전이 실패는 **건별로 격리**해야 한다. 한 주문의 실패가 배치 전체를 멈추면 안 된다.
- **R7.5** 자동으로 상태가 바뀔 때마다 당사자에게 알림을 보내, 사용자가 진행 상황을
  운영자에게 묻지 않아도 알 수 있어야 한다.
- **R7.6** 운영자 화면은 **예외 큐**여야 한다 — 분쟁, 타임아웃 초과, 트래커 장기 미확인 건만
  올라온다. 정상 진행 건은 목록에 뜨지 않는다.

### R8. CS 연락처

- **R8.1** 주문 생성 시 구매자의 **CS 연락 가능한 전화번호**를 수집해야 한다.
- **R8.2** 판매자는 매물 등록 시 또는 프로필에 CS 연락처를 등록해야 한다.
- **R8.3** 전화번호는 형식을 검증하고 정규화해 저장해야 한다(숫자만, 국내 휴대폰/유선).
- **R8.4** 전화번호는 **거래 당사자와 운영자에게만** 노출해야 한다.
  목록·공개 화면에서는 마스킹한다(`010-****-1234`).
- **R8.5** 운영자가 전체 번호를 열람하면 **감사 로그**를 남겨야 한다
  (개인정보 열람 이력 — `admin` 컨텍스트의 감사 기능 재사용).
- **R8.6** 연락처는 거래 분쟁 대응 목적으로만 쓰며, 목적 외 사용을 금지한다는 고지가 있어야 한다.

### R9. 상태별 타임아웃 (R7.2 구체화)

| 상태 | 조건 | 타임아웃(기본) | 자동 처리 |
|---|---|---|---|
| `PAYMENT_PENDING` | 결제 미승인 | 30분 | `PAYMENT_FAILED` 전이 + 매물 예약 해제 |
| `FUNDS_HELD` | 운송장 미등록 | 3일 | 판매자 독촉 알림 |
| `FUNDS_HELD` | 운송장 미등록 | 7일 | **자동 전액 환불** + 매물 복구 |
| `PENDING`(송장 등록됐으나 미접수) | 택배사 미접수 | 3일 | 판매자 알림 + 예외 큐 등재 |
| `IN_TRANSIT` | 배송 정체 | 14일 | 예외 큐 등재(운영자 확인) |
| `DELIVERED` | 무분쟁 | 7일 | **자동 구매확정** + 수수료 확정 + 정산 |
| `DISPUTED` | 운영자 미판정 | 3일 | 운영자 에스컬레이션 알림(자동 판정 없음) |
| 트래커 `UNKNOWN` | 연속 조회 실패 | 24시간 | 예외 큐 등재 |

- **R9.1** 모든 타임아웃 값은 **설정으로 외부화**해야 한다. 코드 상수 금지.
- **R9.2** `DISPUTED`만은 자동 판정하지 않는다. 금전 귀속을 기계가 단정하면 안 되므로
  **사람 판정이 필요한 유일한 상태**로 남긴다(R7.1의 명시적 예외).

### R6. 외부 트래커 연동 제약

- **R6.1** 트래커는 **아웃바운드 포트 뒤에 격리**해야 한다(`DeliveryTrackerPort`).
  외부 API 스펙 변화가 도메인에 새지 않아야 한다.
- **R6.2** 자격증명(API 키)이 없으면 **스텁 어댑터**로 동작하고 앱은 정상 부팅해야 한다
  (`PaymentGatewayPort`의 스텁/실구현 게이트 패턴과 동일).
- **R6.3** 스텁 어댑터는 개발·테스트용으로 상태 전이를 시뮬레이션할 수 있어야 한다.

> **API 키 필요 — 사용자 요청 대기 중.**
> 실 트래커 연동에는 외부 서비스 자격증명이 필요하다. 후보(택배사 통합 조회 API)를
> 사용자가 선정·발급해 주면 env로 주입한다. 그 전까지는 R6.2 스텁으로 전 구간을 완성한다.
> 필요한 값: 트래커 API base URL, API 키/시크릿, 지원 택배사 코드 목록.

## 비고 — 다루지 않는 것

- 플랫폼 검수·정품 인증(`condition-disclosure` 후속에 이미 있음)
- 물류 대행·합배송
- 판매자 정산 실송금(`StubSettlementAdapter` → 실 PG 정산은 `admin-and-payments` 후속)
