# 커뮤니티 신뢰·댓글 운영 (community-trust)

## 목적

커뮤니티 댓글은 공개 대화이지만 신고가 들어왔다는 이유만으로 원문을 삭제하면 운영 근거와 분쟁
증거가 사라진다. 사용자 화면에서는 유해 댓글을 즉시 감출 수 있어야 하고, 관리자는 신고 대상과
부모 게시글이 실제로 일치하는지 확인한 뒤 조치해야 한다.

## 결정

### D1. 댓글 신고는 부모 게시글을 포함한 전용 경로만 사용한다

`POST /api/v1/community/posts/{postId}/comments/{commentId}/report`가 저장된 댓글을 다시 조회해
부모 게시글 일치와 공개 상태를 검증한다. 범용 신고 API에서 `COMMENT`를 직접 받지 않는다. 클라이언트가
임의의 댓글 ID와 게시글 ID를 조합해 운영 문맥을 오염시키지 못하게 하기 위함이다.

### D2. 조치는 삭제가 아니라 블라인드다

댓글 조치 시 `hiddenAt`과 `hiddenReason`을 추가하고 원문·작성자·작성 시각은 보존한다. 공개 댓글 목록은
숨김 댓글을 제외한다. 이미 숨겨진 댓글의 중복 조치는 거부해 조치 사유가 덮어쓰이지 않게 한다.

### D3. 원문 열람 자체가 감사 대상이다

관리자는 신고 큐에서만 댓글 원문과 부모 게시글 링크를 볼 수 있다. 원문 열람은
`COMMENT_REPORT_CONTEXT_VIEW`, 블라인드는 `COMMENT_HIDE`, 신고 종결은 `REPORT_RESOLVE`로 각각 감사
로그에 추가한다. 실패한 조치는 기록하지 않는다.

### D4. 공개 식별자는 댓글 앵커로 연결한다

공개 댓글은 `comment-{commentId}` 앵커를 가진다. 관리자가 부모 게시글로 이동할 때 정확한 대상 위치를
가리키되, 이미 블라인드된 댓글이면 공개 화면에는 앵커와 원문이 모두 나타나지 않는다.

### D5. 반응은 토글이며 새로고침 뒤에도 개인 상태를 복원한다

좋아요 등록은 `POST`, 취소는 같은 경로의 `DELETE`로 제공한다. 공개 피드·게시글 응답의
`likedByViewer`는 유효한 세션이 있을 때만 계산하고, 비로그인·만료 세션은 공개 조회 자체를 막지 않는다.
Next 서버 컴포넌트는 브라우저 쿠키를 API로 자동 전달하지 않으므로 `gole_session` 하나만 명시적으로
전달한다. 분석 쿠키 등 전체 Cookie 헤더를 프록시하지 않는다.

### D6. 작성자 삭제도 물리 삭제가 아니라 소프트 삭제다

댓글 작성자는 자신의 댓글만 삭제할 수 있다. 삭제 요청은 댓글 원문을 제거하지 않고
`hiddenAt`과 `hiddenReason=\"작성자가 삭제함\"`을 기록해 공개 목록에서 제외한다. 다른 사용자는
작성자 삭제 경로를 호출할 수 없고, 이미 운영 블라인드된 댓글의 조치 사유도 덮어쓰지 않는다.

## 요구사항

- [x] R1. 로그인 사용자는 공개 댓글을 전용 경로로 신고할 수 있다.
- [x] R2. 존재하지 않는 댓글, 다른 부모 게시글의 댓글, 이미 숨겨진 댓글은 신고할 수 없다.
- [x] R3. 관리자는 신고 큐에서 원문·작성자·작성 시각·부모 게시글을 확인할 수 있다.
- [x] R4. 원문 열람과 블라인드 조치는 별도 감사 로그로 남는다.
- [x] R5. 블라인드는 원문을 보존하면서 공개 댓글 목록에서 즉시 제외한다.
- [x] R6. 신고 조치와 신고 종결은 하나의 관리자 동작으로 수행한다.
- [x] R7. 댓글 신고 UI는 댓글에 맞는 사유만 표시하고 전용 API만 호출한다.
- [x] R8. 좋아요는 같은 버튼에서 등록·취소할 수 있고 중복 클릭으로 수가 부풀지 않는다.
- [x] R9. 로그인 사용자의 좋아요 상태는 피드 새로고침 뒤에도 선택 상태로 복원된다.
- [x] R10. 공개 GET의 만료 세션은 비로그인 응답으로 강등하고 피드 열람은 유지한다.
- [x] R11. 작성자는 자신의 댓글을 공개 목록에서 삭제할 수 있지만 원문은 보존된다.
- [x] R12. 다른 사용자는 작성자 삭제 경로로 댓글을 숨길 수 없다.

## 수용 기준

- 댓글 A가 게시글 P에 속할 때, 게시글 Q 경로로 A를 신고하면 400이며 신고 레코드는 생기지 않는다.
- 숨김 전 관리자 문맥 조회는 원문과 `hidden=false`를 반환하고 열람 감사 로그를 1건 남긴다.
- 블라인드 후 공개 `GET /posts/{postId}/comments`에는 대상 댓글이 없지만, 관리자 문맥 조회에는 같은
  원문과 `hidden=true`, 최초 조치 사유가 남는다.
- 신고 큐에서 블라인드와 신고 종결이 성공하면 `COMMENT_HIDE`와 `REPORT_RESOLVE`가 각각 한 번 기록된다.
- 사용자가 댓글 신고를 제출할 때 요청 본문에는 `reason`과 `detail`만 있고 `targetId`나 조작 가능한
  부모 ID를 중복 전달하지 않는다.
- 작성자 삭제 후 공개 댓글 수는 즉시 감소하고 새로고침 뒤에도 댓글이 다시 노출되지 않는다.
- 작성자 삭제 원문과 최초 삭제 사유는 저장소에 남고, 권한 없는 사용자의 삭제 요청은 403이다.

## 실제 런타임 검증

2026-09-03 로컬 런타임(`web :3010`, `api :8090`)에서 관리자 세션으로 다음 흐름을 확인했다.

1. 실제 게시글에 댓글을 등록하고 댓글 전용 신고를 접수했다.
2. 어드민 신고 큐가 4건에서 5건으로 증가하고 원문·작성자·부모 게시글 문맥을 표시했다.
3. 사유를 입력해 `블라인드 후 완료`를 실행하자 접수 큐가 다시 4건이 됐다.
4. 부모 게시글의 공개 댓글 수가 1건에서 0건으로 바뀌었다.
5. 감사 로그에 `COMMENT_REPORT_CONTEXT_VIEW`, `COMMENT_HIDE`, `REPORT_RESOLVE` 세 기록이 남았다.

같은 런타임에서 실제 게시글의 좋아요를 등록해 `1개`를 확인하고 새로고침한 뒤 선택 상태가 복원되는
것을 확인했다. 취소 후 다시 새로고침했을 때도 `0개`와 미선택 상태가 유지됐다. 검증이 끝난 테스트
반응은 취소해 시드 데이터를 원래 상태로 돌렸다.

같은 런타임에서 작성자 계정으로 실제 댓글을 등록한 뒤 `삭제`를 실행했다. 공개 댓글 수가 1건에서
0건으로 즉시 바뀌었고, 게시글을 다시 불러온 뒤에도 댓글 수 0건과 원문 비노출 상태가 유지됐다.
서비스 단위 테스트로 저장 원문 보존과 다른 사용자 삭제 거부도 함께 고정했다.

## 후속

- 신고·차단 지표가 충분히 쌓인 뒤 반복 위반 사용자에 대한 단계적 제한 정책을 별도 스펙으로 정한다.
