# 설계

## 도메인과 저장

- `SupportNoticeKind`: PROGRESS / RESULT. 일반 답변은 null이며 기존 API 요청과 호환된다.
- `SupportNotice`: kind, messageId, senderId, sentAt. 본문·이메일을 복제하지 않는다.
- `SupportTicket.notices`: 불변 안내 기록 목록. 구버전 문서/생성자는 빈 목록으로 읽는다. 모든 기존 상태 전이는 이 목록을 보존한다.
- 결과/처리방안 안내는 진행 상황을 포함하므로 진행 목표의 최초 근거가 될 수 있다. 각 목표는 해당하는 최초 메시지 시각으로 비교한다. 목표와 같은 시각은 목표 내다.
- PROGRESS는 72시간 목표·24시간 전 임박, RESULT는 240시간 목표·48시간 전 임박이다. 목표보다 현재 시각이 늦으면 즉시 초과다. 날짜 반올림으로 초과 첫날을 숨기지 않는다.

## 쓰기 트랜잭션

`SupportConsoleUseCase`에 종류가 있는 답변을 추가한다. 기존 답변은 일반 답변으로 남는다. `SupportChatService`가 현재 담당자 검사 → 실제 메시지 저장 → 변경된 최신 티켓 재조회 → 메시지에서 안내 기록 생성 → 티켓 저장 → 감사 순으로 처리한다. `ChatMessagingService`가 먼저 상태/버전을 올리므로 오래된 티켓을 재저장하지 않는다. 기존 afterCommit SSE와 Mongo 트랜잭션을 유지한다.

별도의 발송 완료 체크 API는 만들지 않는다. 일반 답변과 내부 메모는 안내 원장에 넣지 않는다. 해결/재개 API의 기존 계약을 유지하되 해결한 미기록 티켓은 콘솔에서 명확히 알리고 재개 후 안내할 수 있게 한다.

## 읽기와 전체 집계

- 기존 인박스에 `notice` 필터(PROGRESS_DUE_SOON / PROGRESS_OVERDUE / RESULT_DUE_SOON / RESULT_OVERDUE)를 추가한다. 선택 시 기존 상태·유형과 AND하고 접수 순으로 조회한다.
- 별도 `/api/admin/support/notice-summary`는 전체 보존 티켓을 서버에서 집계한다. 목록 한도로 잘라 클라이언트에서 계산하지 않는다.
- 각 안내의 `pending/dueSoon/overdue/onTime/late`는 서로 겹치지 않는다. 전체 합이 total과 같아야 한다. 시간은 서버 Clock 하나를 사용한다.
- Mongo aggregation에서 기존 문서의 빈/누락 notices를 처리하고 최초 시각·접수 목표를 계산한다. 큐 조회는 안내 유무와 createdAt 경계를 먼저 검사하고 한도를 적용한다.
- 메타데이터 응답은 최초 안내 시각만 노출한다. 상세 안내 이력은 담당자만 읽으며 메시지 본문은 기존 대화 접근 규칙을 따른다.

## 화면

기존 브랜드를 확장한다. 흰색(#FFFFFF)·neutral-900(#18181B)·brand-600(#1D4ED8)·brand-50(#EFF4FF)와 warning/danger/success 의미 토큰만 사용한다. SUITE 제목, SUIT 본문과 숫자이며 모두 왼쪽 정렬한다.

```text
운영 문의                     새로고침
진행 안내  [임박 N] [초과 N]   목표 내 N / 목표 후 N
결과 안내  [임박 N] [초과 N]   목표 내 N / 목표 후 N
집계 기준 시각 · 보존 문의 전체
상태 / 유형 / 안내 목표 필터
문의 목록 | 선택 문의: 상태·목표와 실제 이행
          | 대화 / 안내 이력 / 내부 메모
          | 답변 종류 → 답변 내용 → 보내기
```

임박/초과 수치는 행동 가능한 필터로 연결한다. 장식용 지표 카드나 그래프를 늘리지 않고 두 안내 목표를 읽는 표형 요약으로 구성한다. 모바일은 두 행을 세로 배치하고 기존 목록/대화 전환을 유지한다. 실제 안내 이력이 없으면 해결 시각으로 녹색 성공을 만들지 않는다.

## 검증

- 도메인과 서비스/MVC: 최초 안내·일반 답변·시간 경계·반복/재개·구버전·담당자·잘못된 종류·클라이언트 시각 무시.
- Testcontainers: 트랜잭션 저장/롤백과 버전 갱신, 최신100건 밖 큐·전체 집계, 필터 교차·구버전·파기 후 안내 제거.
- 웹: 요약/필터/안내 종류와 실제 이행, 오류 복구·내용 보존, 담당자 외 열람 차단 유지, 반응형·키보드.
- 별도 E2E 데이터/API8093/WEB3003과 Orca 독립 탭을 사용하며 외부 발송·실결제는 비활성화한다.

## 검토 반영 계약

기획 Claude와 디자인 Codex의 읽기 검토를 감독자가 확인했다. 해결·미기록 큐 가림, 모바일 목록 자동 복귀, 조회 상태 혼동, 초안 손실을 이번 R8/R9 확장으로 채택한다.

- `noticeScope=ALL|ACTIVE|RESOLVED`를 추가한다. 기본 ALL은 기존 필터 호환이며, 화면의 임박/초과 버튼은 ACTIVE를 보낸다. 해결 미기록 버튼은 RESOLVED와 `PROGRESS_MISSING|RESULT_MISSING`를 보낸다.
- 집계의 기존 전체 다섯 분류를 유지하고 미해결 분류·해결 미기록 건수를 추가한다. 해결 여부와 안내 이행 여부를 혼동하지 않는다.
- 필터 요청 시작에는 이전 목록·선택을 닫고, 실패 시 재시도를 제공한다. 같은 필터의 갱신 실패에는 마지막 성공 목록임을 명시한다.
- 첫 로드의 선택과 사용자가 목록을 선택한 상태를 구분한다. 문의별 초안은 화면의 메모리에만 두며 권한 상실/계정 변경 시 버린다.
- 감사 포트 자체의 실패를 흡수하는 기존 admin-console R8.5는 유지한다. 조치 트랜잭션 롤백 시 메시지·안내·성공 감사와 SSE가 함께 남지 않는 것을 검증한다.
