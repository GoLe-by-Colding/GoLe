# 가입 정책 확인 증빙

상태: 구현·로컬 검증 중
기준일: 2026-09-03

## 배경

이용약관·개인정보처리방침 페이지가 있어도 가입 순간 어떤 문서를 확인했는지 남지 않으면
운영자가 동의 경위를 재현할 수 없다. 반대로 모든 개인정보 처리를 하나의 필수 “동의”로
묶으면 선택권을 흐릴 수 있다. GoLe는 가입에 필요한 항목을 화면에서 분리하고, 개인정보
처리방침은 “확인”으로 표현하며, 선택 마케팅 동의는 이 흐름에 넣지 않는다.

법률 최종 판단은 출시 전 전문가 검토 대상이다. 구현 근거는 개인정보 보호법 제22조와
동의 방법을 구체화한 시행령 제17조의 명확성·가독성 원칙이다.

- [개인정보 보호법 제22조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0022&lsiSeq=270351&urlMode=lsScJoRltInfoR)
- [개인정보 보호법 시행령 제17조](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1013462601)
- [개인정보보호위원회 개인정보 처리 동의 안내서](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010030000&nttId=7912)

## 결정

### D1. 현재 정책은 서버가 원본이다

`GET /api/v1/policies/current`가 이용약관 버전, 개인정보처리방침 버전, 최소 가입 연령을
반환한다. 가입 폼은 이 응답을 받기 전에는 제출할 수 없다. 서버 설정의 기본 버전은 문서
시행일과 같은 `2026-09-03`이며, 문서를 바꿀 때 함께 올린다.

### D2. 확인 항목을 분리한다

가입 화면은 다음 세 항목을 각각 확인한다.

1. 이용약관 동의
2. 개인정보처리방침 확인
3. 만 14세 이상 확인

하나의 “전체 동의”만 두지 않는다. 약관·처리방침은 새 탭으로 원문을 열 수 있어야 한다.

### D3. 서버가 버전과 불리언을 다시 검증한다

이메일 가입 요청은 다섯 필드(`termsVersion`, `privacyVersion`, `termsAccepted`,
`privacyAcknowledged`, `minimumAgeConfirmed`)를 보낸다. 하나라도 거짓이면
`POLICY_ACCEPTANCE_REQUIRED`, 현재 버전과 다르면 `POLICY_VERSION_STALE` 400이다.
클라이언트의 버튼 비활성만 보안 경계로 삼지 않는다.

### D4. 증빙은 계정과 분리된 append-only 이력이다

`policy_acceptances`에는 계정 ID, 두 문서 버전, 세 확인값, 가입 채널, 서버 수락 시각을
추가한다. 계정 문서 수정으로 과거 증빙을 덮지 않는다. 동일 계정·동일 문서 버전은 고유
인덱스로 멱등 처리한다. 원시 IP·User-Agent는 이 컬렉션에 중복 저장하지 않는다.

이메일 계정과 증빙 생성은 같은 Mongo 트랜잭션이다. 증빙 저장 실패 뒤 계정만 남는
부분 성공을 허용하지 않는다.

### D5. 소셜 신규 가입도 같은 규칙을 쓴다

회원가입 탭에서 소셜 버튼을 누를 때 정책 확인값을 OAuth state의 서버측 문맥에 저장한다.
콜백은 state를 1회 소비하고 provider·redirect URI를 다시 대조한 뒤 신규 계정과 증빙을
같은 트랜잭션으로 만든다. 로그인 탭에서 기존 계정을 소셜 로그인할 때는 재확인을 요구하지
않지만, 확인 정보 없이 처음 발견된 소셜 계정을 자동 생성하지 않는다.

## 수용 기준

- [x] 정책 공개 API는 세션 없이 호출 가능함
- [x] 이메일 가입은 최신 버전·세 필수 확인이 없으면 계정을 만들지 않음
- [x] 이메일 계정과 정책 증빙이 같은 트랜잭션에 참여함
- [x] 소셜 OAuth state가 정책 확인값과 provider·redirect URI를 함께 결박함
- [x] 기존 소셜 계정 로그인은 정책 재확인 없이 유지됨
- [x] 신규 소셜 계정은 정책 확인 정보가 없으면 생성되지 않음
- [x] 실제 `:3010` 가입 UI와 `:8090` Mongo 이력 생성 검증
- [x] 계정 단위 백엔드 테스트·프론트 정적 검사·인증 E2E 통과
- [x] 전체 백엔드 회귀 테스트 통과

## 2026-09-03 로컬 런타임 증빙

- 세션 없는 `GET /api/v1/policies/current` → 200, 두 버전 `2026-09-03`, 최소 연령 14
- 약관 미동의 가입 → 400 `VALIDATION_ERROR`, Mongo 계정 0건
- 세 항목을 확인한 이메일 가입 → 201, 계정과 `policy_acceptances` 각 1건
- 증빙 채널 `EMAIL`, 서버 시각·두 버전·세 확인값 저장 확인
- Orca 내장 브라우저에서 세 체크 전 가입 버튼 비활성, 모두 확인 후 활성 확인
- Chromium 전체 E2E 121건 통과(환경 의존 7건은 의도적으로 skip)
- 백엔드 전체 테스트와 Spotless 검사 통과

## 운영 체크

- 약관 또는 처리방침 변경 배포에서 문서 시행일과 `GOLE_TERMS_VERSION` /
  `GOLE_PRIVACY_VERSION`을 한 변경 묶음으로 검토한다.
- 버전 변경 직전 열려 있던 가입 화면은 stale 오류로 닫히며, 새로고침 후 다시 확인한다.
- 과거 이력 정정이 필요하면 기존 행을 수정하지 않고 별도 관리자 감사 조치로 남긴다.
