# 모바일 앱 (React Native) — 요구사항

## 개요

GoLe는 현재 웹(Next.js)만 있다. 이 스펙은 **iOS·Android 네이티브 앱**을 추가하고, 그 과정에서
웹과 앱이 공유하는 **플랫폼 중립 코어 패키지**를 분리한다.

핵심 판단은 "무엇을 공유하느냐"다. 화면(UI)은 공유하지 않는다 — 웹은 Tailwind + DOM이고 앱은
네이티브 뷰라 억지로 합치면 양쪽 다 나빠진다. 대신 **엔티티 모델과 API 호출**은 한 벌만 둔다.
백엔드 스펙이 바뀔 때 고칠 곳이 두 곳이면 반드시 어긋난다.

## 현재 상태 (실측 기준선)

**공유 가능한 코드 — 약 3.8k LOC**

| 대상 | 규모 | 상태 |
|---|---|---|
| `entities/*/{api,model}` | 3,187 LOC / 15 슬라이스 | 순수 TS. `ui/`를 가진 슬라이스는 2개(`lego-set`·`listing`) |
| `shared/{api,lib,config}` | 641 LOC | fetch 기반 |

엔티티 레이어의 외부 의존은 **전부 합쳐 19건**이다.

| import | 건수 |
|---|---|
| `apiRequest` (`@shared/api`) | 15 |
| `PaymentMethod` · `formatKrw` (`@shared/lib`) | 3 |
| `clearStoredSession` · `SESSION_*` (`@shared/api`) | 1 |
| `env` (`@shared/config`) | 1 |

FSD를 엄격히 지킨 결과 엔티티 레이어가 이미 사실상 플랫폼 중립 SDK다. 이 스펙은 그것을
**드러내는** 작업이지 새로 만드는 작업이 아니다.

**공유 불가 — 다시 짜야 하는 것**

`shared/ui` 17개 컴포넌트, `widgets` 14개, `views` 23개, `features` 20개. 전부 DOM이다.

**플랫폼에 묶인 3곳 — 코어로 옮기려면 풀어야 한다**

1. `shared/api/session-auth.ts` — `window.localStorage`를 모듈 안에서 직접 읽는다.
2. `shared/config/env.ts` — `process.env.NEXT_PUBLIC_*`을 모듈 스코프에서 읽고 동결한다.
3. `shared/api/upload-client.ts` — `File`과 브라우저 `FormData`를 전제한다.

`shared/lib/portone.ts`는 절반만 묶여 있다. `buildPortOnePaymentRequest`는 이미 `origin`을
인자로 받아 순수하고, 실제 SDK 호출은 `requestPortOnePayment` 하나뿐이다.

**웹에 남아야 하는 것**: `class-names.ts`(Tailwind), `seo.ts`(next), `server-session-headers.ts`
(`next/headers` + `server-only`).

**백엔드는 거의 손댈 게 없다 (실측)**

- `SessionCookie.resolve()`가 **Bearer를 먼저 읽고 쿠키로 폴백**한다. 앱은 Bearer만 쓰면 되고
  인증 경로 변경이 필요 없다.
- CORS(`gole.web.allowed-origins`)는 네이티브 fetch에 적용되지 않는다.
- 소셜 로그인의 `redirectUri`는 클라이언트가 보내고 서버는 저장된 state와의 **일치만** 검증한다
  (`SocialAuthService:101`). 앱 전용 redirect URI를 백엔드 변경 없이 쓸 수 있다.
- 이미지 공개 URL이 API 원점(`STORAGE_PUBLIC_BASE_URL`)이라 CSP `img-src` 제약이 앱에는 없다.

**백엔드에 없는 것**: 푸시 알림 인프라가 전무하다. FCM·APNs 참조가 0건이고 `notification`
컨텍스트의 아웃바운드 어댑터는 coolsms(SMS·알림톡)뿐이다.

## 용어

| 용어 | 의미 |
|---|---|
| 코어(core) | `packages/core`. 웹·앱이 함께 쓰는 플랫폼 중립 TS 패키지 |
| 부트스트랩 | 앱 시작 시 코어에 환경설정과 플랫폼 어댑터를 주입하는 1회 호출 |
| 세션 저장소 | 세션 토큰 보관 추상. 웹은 localStorage, 앱은 SecureStore |
| 채널 짝짓기 | 결제수단 하나가 채널 키와 `payMethod`를 함께 정하는 규칙 |

## 요구사항

### R1. 공유 코어 패키지

- **R1.1** `packages/core`는 웹·앱 어느 쪽에도 의존하지 않아야 한다. `next`, `react`,
  `react-native`, DOM 전역을 import하지 않는다.
- **R1.2** 엔티티 15개 슬라이스의 `model`·`api`를 코어가 전부 포함해야 한다. 웹과 앱이 같은
  타입·같은 호출을 쓴다.
- **R1.3** 세션 토큰 접근은 **주입된 세션 저장소**를 거쳐야 한다. 코어가 `window`를 참조하면 안 된다.
- **R1.4** API 원점 등 환경값은 **부트스트랩에서 주입**해야 한다. 코어가 `process.env`를 읽으면 안 된다.
- **R1.5** 부트스트랩 전에 코어 API를 호출하면 조용히 기본값으로 넘어가지 말고 **던져야** 한다.
  API 원점이 빈 문자열이면 요청이 엉뚱한 곳으로 가고 원인이 드러나지 않는다.
- **R1.6** 이미지 업로드는 `File`과 네이티브 파일 참조를 **모두** 받을 수 있어야 한다.
- **R1.7** 웹은 마이그레이션 후에도 기존 품질 게이트 5종(`format:check`·`lint`·`typecheck`·
  `fsd:lint`·`build`)을 그대로 통과해야 한다. 화면 동작이 바뀌면 안 된다.
- **R1.8** 코어는 웹의 tsconfig strict 풀세트(`noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`)와 **같은 수준**으로 검사해야 한다.

### R2. 모바일 앱 셸

- **R2.1** `apps/mobile`은 pnpm 워크스페이스 구성원이어야 하고 `packages/core`를 워크스페이스
  의존으로 참조해야 한다.
- **R2.2** 하단 탭은 홈·검색·판매·채팅·내 정보 5개여야 한다.
- **R2.3** 브랜드 색·타이포는 `globals.css`의 `@theme` 토큰과 **같은 값**을 써야 한다.
  시세 등락색(`rise` 빨강 / `fall` 파랑)의 한국 관례도 그대로 따른다.
- **R2.4** iOS·Android 모두에서 빌드되어야 한다.

### R3. 인증

- **R3.1** 이메일·비밀번호 로그인·회원가입·로그아웃이 동작해야 한다.
- **R3.2** 세션 토큰은 **암호화 저장소**(Keychain·Keystore)에 보관해야 한다. 앱은 브라우저와
  달리 기기 분실 시 파일 접근 위험이 있으므로 평문 저장은 허용하지 않는다.
- **R3.3** 앱은 쿠키가 아니라 `Authorization: Bearer`로 인증해야 한다.
- **R3.4** 서버가 `401 INVALID_SESSION`을 주면 저장된 세션을 폐기하고 로그인 화면으로 보내야 한다.
  다른 401(예: `INVALID_CREDENTIALS`)은 로그아웃으로 해석하지 않는다 — 웹과 같은 규칙이다.
- **R3.5** 앱 재시작 후에도 로그인 상태가 유지되어야 한다.

### R4. 소셜 로그인

- **R4.1** Google·Kakao·Naver 로그인이 앱에서 동작해야 한다.
- **R4.2** provider별 **네이티브 client ID**와 커스텀 스킴 redirect를 쓴다. 백엔드는 변경하지 않는다.
- **R4.3** 백엔드에 client-id가 설정되지 않은 provider는 웹과 같이 **비활성**으로 노출해야 한다.
- **R4.4** state는 서버가 발급·검증한 값을 그대로 왕복시켜야 한다(CSRF). 앱이 새로 만들지 않는다.
- **R4.5** 사용자가 동의 화면을 취소하면 오류가 아니라 취소로 안내해야 한다.

### R5. 읽기 화면

- **R5.1** 홈, 검색(필터 포함), 매물 상세, 세트 상세·시세, 셀러샵, 커뮤니티 목록·글, 알림함,
  주문 상세, 컬렉션을 볼 수 있어야 한다.
- **R5.2** 목록은 페이지네이션 또는 무한 스크롤로 동작해야 한다. 웹의 "전체를 받아 클라이언트에서
  거르기"를 앱으로 옮기면 안 된다.
- **R5.3** 이미지는 썸네일 규칙(`thumbnailUrl`)을 웹과 공유해야 한다.
- **R5.4** 네트워크 실패 시 빈 화면이 아니라 재시도 가능한 오류 상태를 보여야 한다.

### R6. 쓰기 화면

- **R6.1** 매물 등록이 동작해야 한다. 사진은 카메라·앨범 양쪽에서 고를 수 있어야 한다.
- **R6.2** 다중 이미지 업로드는 기존 `POST /api/v1/media/images/batch`를 써야 한다.
- **R6.3** 찜, 셀러 팔로우, 커뮤니티 글·댓글 작성, 좋아요, 신고, 리뷰 작성이 동작해야 한다.
- **R6.4** 1:1 채팅으로 문의하고 대화할 수 있어야 한다.
- **R6.5** 운송장 등록, 분쟁 접수가 동작해야 한다.

### R7. 결제

- **R7.1** 구매자가 카카오페이·카드 중 하나로 결제할 수 있어야 한다.
- **R7.2** **결제수단과 채널 키·`payMethod`의 짝짓기 규칙은 웹과 한 벌을 공유해야 한다.**
  서버가 이 짝을 검증하므로 앱만 다른 조합을 보내면 전부 `PAYMENT_REVIEW`로 떨어진다.
- **R7.3** 카드 결제 시 이름·이메일·연락처 확인 단계를 거쳐야 한다(웹의 R2와 동일 제약).
- **R7.4** 포트원 설정이 없으면 결제 버튼을 **비활성**으로 노출해야 한다. 스텁으로 조용히
  우회하면 안 된다.
- **R7.5** 결제창 응답 뒤 반드시 서버 원장 검증 경로를 거쳐야 한다. 앱이 성공을 확정하지 않는다.
- **R7.6** 결제창을 닫아 취소한 경우와 실제 장애를 구분해 안내해야 한다.

### R8. 푸시 알림

- **R8.1** 앱은 디바이스 토큰을 서버에 등록·해제할 수 있어야 한다.
- **R8.2** 백엔드는 알림 발행 시 기존 채널(인앱·SMS)에 더해 푸시를 보낼 수 있어야 한다.
- **R8.3** 푸시 발송 실패가 주 트랜잭션을 실패시키면 안 된다.
- **R8.4** 푸시를 탭하면 해당 화면으로 이동해야 한다.
- **R8.5** 푸시 설정이 없는 환경에서 기동이 실패하면 안 된다. 푸시만 닫힌다.

### R9. CI / 릴리스

- **R9.1** `ci.yml`에 모바일 잡(lint·typecheck)을 추가해야 한다.
- **R9.2** `packages/core`는 웹·모바일 잡 양쪽에서 검사되어야 한다.
- **R9.3** **`cd.yml`을 변경하지 않는다.** pm2 배포와 앱스토어 릴리스는 다른 경로다.
  앱 릴리스는 별도 수동 워크플로로 둔다.
- **R9.4** `AGENTS.md`의 프로젝트·명령어·아키텍처 절을 새 구조에 맞게 고쳐야 한다(정본 규칙).

## 범위 밖

- **관리자 콘솔.** 웹 `views/admin`(13개 클라이언트 파일)은 앱에 옮기지 않는다. 관리자는 웹을 쓴다.
- **react-native-web / UI 공유.** 화면은 플랫폼별로 따로 짠다.
- **웹 UI 재작성.** 이 스펙은 웹의 화면을 바꾸지 않는다(R1.7).
- **오프라인 모드·로컬 캐시 DB.** 온라인 전제로 만든다.
- **태블릿 전용 레이아웃.**
- **결제 LIVE 전환.** 운영은 포트원 공개 설정 없이 빌드돼 결제가 닫혀 있고 카드는 TEST 채널뿐이다.
  앱 결제가 웹보다 먼저 열릴 수는 없다.
- **SEO·딥링크 웹 폴백.** Universal Links는 R4에서 커스텀 스킴을 택했으므로 쓰지 않는다.
