# 거래 흐름 보완 설계

## 확인한 끊김

- `listing-detail-page.tsx`는 `active`가 아니면 모두 거래완료로 표시한다. 예약 상태가 잘못 전달된다.
- `OrderController`·`OrderService`·core API에 결제 대기 취소 계약이 없다. 구매자가 주문을 포기해도 예약 만료 전 직접 해제할 수 없다.
- 주문 화면의 `pay()`는 최신 주문을 조회하지만 상태를 검사하지 않고 결제창을 연다.
- 판매자의 배송 현황 전체가 `funds_held` 조건 안에 있어 완료·분쟁 후 운송장 확인 동선이 사라진다.

## 주문 취소

`CancelOrderUseCase`를 추가하고 `POST /api/v1/orders/{id}/cancellation`은 구매자 권한을 확인한다. 서비스는 PG 네트워크 조회를 트랜잭션 밖에서 실행한다. 결제 없음/최종 실패만 `OrderPaymentTransitionService`의 짧은 트랜잭션에서 최신 주문을 다시 읽고 `PAYMENT_PENDING → CANCELLED`와 예약 복원을 함께 저장한다. 이미 CANCELLED면 같은 결과를 반환한다.

승인된 결제는 기존 승인 전이를 반영하고 취소를 거부한다. 진행·검토·장애도 취소 성공으로 처리하지 않는다. 로컬 스텁의 승인 시뮬레이션과 취소용 읽기 조회를 분리한다.

취소 후 늦은 승인은 `CANCELLED → REFUND_PENDING → REFUNDED`로 회수한다. 취소 이력이 있는 환불은 이미 예약을 풀었으므로 매물에 다시 release를 호출하지 않는다. 웹훅 및 취소 주문 원장 재조정으로 지연 승인을 처리한다. 운영 원장이 불명확하면 기존 검토 오류와 운영 신호를 보존한다.

취소 주문의 스케줄러도 취소용 읽기 조회를 사용한다. 스텁에서 일반 승인 시뮬레이션을 호출해 결제 없는 취소를 환불로 바꾸지 않는다. `CANCELLED`는 지연 승인 가능성이 남으므로 `isTerminal`에 포함하지 않아 운영팀 문의의 거래 증거 파기 차단을 유지한다. 계정 탈퇴 어댑터는 별도의 활성 상태 목록을 쓰며 주문 레코드를 삭제하지 않으므로 주문 ID 기반 지연 환불을 유지한다.

PortOne 결제 조회·취소 계약 근거: https://developers.portone.io/api/rest-v2/payment?v=v2 (2026-10-21 확인). 외부 결제창을 연 뒤 즉시 중단시키는 것으로 가정하지 않고 지연 승인 보상 경로를 둔다.

## 화면

core에 cancelled 상태·라벨·취소 API를 노출한다. 주문 화면의 공통 확인 모달에서 취소·구매확정·환불을 처리하고 응답 주문을 표시한다. 취소는 결제 공개 토글과 무관하게 기존 주문의 구매자에게 제공한다. 결제 시작은 최신 서버 주문 상태와 공개 토글 모두를 재확인한다.

취소된 주문에도 상태 재조회 동선을 남겨 지연 승인에 따른 환불 상태를 확인할 수 있게 한다.

예약 매물은 예약 중으로 표시한다. 배송 조회와 운송장 편집 권한을 분리해 종결 주문에서도 조회를 유지한다. 실제 결제 계약 및 운영 데이터 검증은 수행하지 않는다.
