# 개인정보 권리 요청 운영 (privacy-rights-operations)

## 왜 필요한가

개인정보처리방침에 이메일 주소만 적어 두면 요청 접수 이후의 담당자·상태·응답 목표를 서비스가
추적하지 못한다. GoLe는 로그인 사용자가 서비스 안에서 권리 요청을 접수하고, 기존 운영 문의의
배정·이관·내부 메모·감사 로그를 그대로 사용해 누락을 막는다.

이 구현은 법률 자문을 대신하지 않는다. 출시 전 개인정보 보호책임자 정보, 실제 보유 항목과
보존 기간, 처리 거절·제한 및 이의제기 절차를 전문가가 다시 검토해야 한다.

## 결정

### D1. 요청은 SUPPORT 방의 분류로 남긴다

별도 이메일 티켓 저장소를 만들지 않고 이미 개인정보 최소 열람·담당자 배정·감사 로그가 적용된
운영 문의를 확장한다.

| 분류                          | 용도                                  |
| ----------------------------- | ------------------------------------- |
| `GENERAL`                     | 일반 이용 문의와 구버전 데이터 기본값 |
| `TRADE`                       | 거래·직거래                           |
| `PAYMENT`                     | 결제·환불                             |
| `PRODUCT_FEEDBACK`            | 기능 제안·불편 신고                   |
| `PRIVACY_ACCESS`              | 개인정보 열람                         |
| `PRIVACY_CORRECTION_DELETION` | 개인정보 정정·삭제                    |
| `PRIVACY_PROCESSING_STOP`     | 개인정보 처리정지·동의 철회           |

### D2. 요청 생성 자체가 본인 확인의 1차 증거다

인증된 세션의 `accountId`를 요청자로 서버가 기록한다. 주민등록번호·신분증 이미지는 받지 않는다.
대리인 요청이나 추가 본인 확인이 필요한 예외는 운영팀이 동일 대화에서 최소 정보만 추가로 안내한다.

### D3. 개인정보 요청은 생성 시각 + 10일을 운영 목표로 표시한다

`responseDueAt`은 개인정보 권리 요청에만 계산한다. 어드민 인박스는 남은 일수·기한 초과·기한 내
완료 여부를 표시한다. 이 값은 자동 삭제·자동 승인이나 법률상 최종 기한 판정을 하지 않는다.

### D4. 삭제는 자동 실행하지 않는다

거래·결제·분쟁·부정 이용 기록은 다른 법령 또는 정당한 보존 목적과 충돌할 수 있다. 요청 접수 시
데이터를 지우지 않고 담당자가 보유 항목과 보존 근거를 확인한 뒤 조치·제한·거절 사유를 대화로
안내한다. 현재 구현은 사용자 데이터 삭제 API를 만들지 않는다.

### D5. 구버전 문의는 끊기지 않는다

Mongo 문서에 `category`가 없는 기존 티켓은 `GENERAL`로 읽고, 일반 필터에도 포함한다.

## 수용 기준

- [x] 사용자 문의 작성기에 7개 분류가 보인다.
- [x] 개인정보처리방침과 프로필에서 로그인 기반 권리 요청으로 진입한다.
- [x] 서버가 요청자 ID·분류·생성 시각을 함께 저장한다.
- [x] 개인정보 권리 요청 응답에는 `responseDueAt`이 있고 일반 문의에는 없다.
- [x] 어드민이 상태와 유형을 함께 필터하고 권리 요청의 남은 기한을 본다.
- [x] 배정 전에는 문의 본문을 열지 않는 기존 최소권한 규칙을 유지한다.
- [x] 기존 무분류 티켓은 일반 문의로 계속 조회된다.
- [ ] 처리 제한·거절 시 구조화된 사유와 이용자 이의제기 절차를 별도 상태로 기록한다.
- [ ] 실제 계정 삭제·익명화는 주문·정산·분쟁 보존 정책 확정 후 별도 스펙으로 구현한다.
