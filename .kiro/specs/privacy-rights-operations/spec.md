# 개인정보 권리 요청 운영 (privacy-rights-operations)

## 왜 필요한가

개인정보처리방침에 이메일 주소만 적어 두면 요청 접수 이후의 담당자·상태·응답 목표를 서비스가
추적하지 못한다. GoLe는 로그인 사용자가 서비스 안에서 권리 요청을 접수하고, 기존 운영 문의의
배정·이관·내부 메모·감사 로그를 그대로 사용해 누락을 막는다.

이 구현은 법률 자문을 대신하지 않는다. 출시 전 개인정보 보호책임자 정보, 실제 보유 항목과
보존 기간, 처리 거절·제한 및 이의제기 절차를 전문가가 다시 검토해야 한다.

## 결정

### D1. 요청은 SUPPORT 방의 분류로 남긴다

별도 이메일 티켓 저장소를 만들지 않고 이미 개인정보 최소 열람·담당자 배정·감사 로그가 적용된
운영 문의를 확장한다.

| 분류                          | 용도                                  |
| ----------------------------- | ------------------------------------- |
| `GENERAL`                     | 일반 이용 문의와 구버전 데이터 기본값 |
| `TRADE`                       | 거래·직거래                           |
| `PAYMENT`                     | 결제·환불                             |
| `PRODUCT_FEEDBACK`            | 기능 제안·불편 신고                   |
| `PRIVACY_ACCESS`              | 개인정보 열람                         |
| `PRIVACY_CORRECTION_DELETION` | 개인정보 정정·삭제                    |
| `PRIVACY_PROCESSING_STOP`     | 개인정보 처리정지·동의 철회           |

### D2. 요청 생성 자체가 본인 확인의 1차 증거다

인증된 세션의 `accountId`를 요청자로 서버가 기록한다. 주민등록번호·신분증 이미지는 받지 않는다.
대리인 요청이나 추가 본인 확인이 필요한 예외는 운영팀이 동일 대화에서 최소 정보만 추가로 안내한다.

### D3. 모든 운영 문의에 진행·처리방안 안내 목표를 표시한다

전자상거래법상 불만·분쟁 기준과 문의 누락 방지를 함께 맞추기 위해 모든 운영 문의에
`progressDueAt`(접수 후 3일)과 `responseDueAt`(접수 후 10일)을 계산한다. 법정 기준인 3영업일·10영업일
보다 이르게 잡는 보수적 내부 목표이며, 개인정보 권리 요청에도 같은 목표를 적용한다. 사용자 문의
응답과 어드민 인박스는 두 목표를 표시하되, 자동 삭제·자동 승인·분쟁 종결 또는 실제 안내 이행을
증명하는 값으로 사용하지 않는다.

### D4. 권리 문의와 계정 탈퇴 실행을 분리한다

거래·결제·분쟁·부정 이용 기록은 다른 법령 또는 정당한 보존 목적과 충돌할 수 있다. 요청 접수 시
문의만으로 데이터를 자동 삭제하지 않고 담당자가 보유 항목과 보존 근거를 확인한 뒤 조치·제한·거절
사유를 대화로 안내한다. 계정 자체의 탈퇴는 별도 강한 본인확인(현재 세션, 이메일 일회성 코드,
현재 이메일과 정확한 확인 문구)을 거쳐 요청하며, 요청 즉시 계정·세션을 비활성화한다. 물리 파기는
관리자가 구조화된 보존 매트릭스를 다시 확인한 경우에만 수행한다.

### D6. 탈퇴 파기는 fail-closed 및 비식별 영수증으로 남긴다

진행 주문·미완료 정산·처리 중 신고·문의 기록·공개 콘텐츠/미디어 수명주기·그룹 소유권 또는 명시적
보존 중지가 남으면 파기를 실행하지 않는다. 완료 시 계정 핵심정보, 동의 이력, 개인화 목록, 세션과
일회성 인증정보를 삭제하고 공유 기록은 삭제 또는 비연결 가명화한다. 완료 원장과 관리자 감사에는
탈퇴 대상 이메일/accountId/자유서술을 남기지 않고 무작위 요청 ID, enum 상태·사유, 시각과 컬렉션별
처리 건수만 남긴다.

### D7. 단일 백엔드에서는 계정별 공정 admission gate로 진행 중 쓰기를 비운다

현재 운영의 API 컨테이너는 한 인스턴스라는 전제다. 유효한 로그인 세션이 실린
`POST`·`PUT`·`PATCH`·`DELETE` 요청은 계정별 공유 lease를 Servlet 요청 완료까지 유지한다.
탈퇴 요청은 같은 계정의 배타 lease를 얻어 이미 진행 중이던 변경 요청을 모두 기다리고, lease를
얻은 뒤 세션과 계정 식별자를 다시 검증한 상태에서 정지 트랜잭션을 실행한다. 공정 대기열이라
탈퇴가 기다리는 동안 뒤늦게 들어온 변경 요청은 앞질러 갈 수 없고, 탈퇴 뒤에는 재검증에서
정지된 세션을 거부한다. 예외와 async 재디스패치 완료 경로에서도 lease를 한 번만 반환한다.

이 프로세스 내부 gate는 다중 API replica 사이에서는 효력이 없다. 수평 확장 전에는 분산
admission gate 또는 데이터베이스 write fence와 동일한 경합 테스트를 도입해야 한다. 세션 없는
공개 인증 흐름과 예약 작업은 이 gate의 대상이 아니므로 각각의 계정 상태 재검증·트랜잭션 및 탈퇴
blocker 계약을 유지하고 변경 시 별도 경합 검토를 거친다.

### D5. 구버전 문의는 끊기지 않는다

Mongo 문서에 `category`가 없는 기존 티켓은 `GENERAL`로 읽고, 일반 필터에도 포함한다.

## 수용 기준

- [x] 사용자 문의 작성기에 7개 분류가 보인다.
- [x] 개인정보처리방침과 프로필에서 로그인 기반 권리 요청으로 진입한다.
- [x] 서버가 요청자 ID·분류·생성 시각을 함께 저장한다.
- [x] 모든 운영 문의 응답에는 `progressDueAt`과 `responseDueAt`이 있고 개인정보 권리 요청에도 같은
      보수적 목표를 적용한다.
- [x] 어드민이 상태와 유형을 함께 필터하고 진행 경과·결과 또는 처리방안 안내 목표를 본다.
- [x] 배정 전에는 문의 본문을 열지 않는 기존 최소권한 규칙을 유지한다.
- [x] 기존 무분류 티켓은 일반 문의로 계속 조회된다.
- [ ] 처리 제한·거절 시 구조화된 사유와 이용자 이의제기 절차를 별도 상태로 기록한다.
- [x] 계정 탈퇴 요청 시 계정 접근과 모든 세션을 즉시 차단한다.
- [x] 진행 거래·정산·신고·문의·콘텐츠 수명주기·명시적 보존 중지를 구조화해 fail-closed 처리한다.
- [x] 관리자만 요청 ID 재입력·보존 검토·멱등성 키를 거쳐 원자적 연계 파기를 실행한다.
- [x] 완료 영수증과 감사 대상에는 탈퇴 대상 이메일/accountId/자유서술을 남기지 않는다.
- [x] 단일 API 인스턴스에서 로그인 기반 변경 요청을 공정 공유 lease로 감싸고 탈퇴가 배타
      lease 뒤 세션을 재검증한다.
- [ ] 다중 API 인스턴스로 확장하기 전에 분산 admission gate 또는 영속 write fence를 도입한다.
