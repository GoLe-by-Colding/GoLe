# 공개 단계 (launch-stage)

## 왜 필요한가

이 서비스는 결제·정산처럼 외부 계약(PG 지급대행, 결제대금예치업)에 묶인 기능을 갖고 있어서
계약이 준비된 순서대로만 열 수 있다. 그런데 "지금 우리가 어디까지 연 상태인가"가 코드에
흩어져 있으면 아무도 한 문장으로 답하지 못하고, 사고가 났을 때 무엇을 닫아야 하는지도
그때그때 찾아야 한다.

이 스펙은 공개 범위를 **DB에 저장되는 운영 설정 하나**로 모은다. 배포 없이 열고 닫는다.

## 결정

### D1. 단계는 0~3, 거래 모델이 함께 따라온다

| 단계            | 거래 모델           | 플랫폼이 돈을 만지는가 | 열리는 것                                            |
| --------------- | ------------------- | ---------------------- | ---------------------------------------------------- |
| 0 `PREPARING`   | `DIRECT_CHAT`       | 아니오                 | 공사중                                               |
| 1 `BROWSE_ONLY` | `DIRECT_CHAT`       | 아니오                 | 매물 열람·커뮤니티·기존 채팅                         |
| 2 `TRADING`     | `MANUAL_SETTLEMENT` | 예                     | + 주문·결제·정산 원장(서면 허용 범위 안의 운영 지급) |
| 3 `FULL`        | `PARTNER_PAYOUT`    | 예                     | + 자동 지급                                          |

**0~1단계는 "결제가 빠진 에스크로"가 아니다.** 플랫폼이 대금을 보유하지 않고 당사자가 직접
만나 거래하는 당근형 모델이며, 서버가 하는 일은 매물과 채팅을 잇는 것까지다. 이걸 "결제가 꺼진
상태"로 부르면 존재하지도 않는 주문·정산 상태를 화면과 코드가 가정하게 된다. 플랫폼이 대금을
수취·보관하지 않는 구조임을 제품과 약관에서 일치시켜야 하며, 실제 사업 형태에 적용되는 신고·중개자
의무는 출시 전 전문가와 별도로 확인한다.

`tradeMode`는 단계에서 **파생**되며 따로 저장하지 않는다. 저장하면 "2단계인데 직거래" 같은
어긋난 조합이 표현 가능해지고, 그 조합에서 주문 API를 열지 말지가 어디에도 정의돼 있지 않다.

### D2. 기능별 override 는 삼상태

기능은 단계 기본값을 따르되, 운영 중 예외가 필요하면 단건만 뒤집는다. override 는
"값 없음 / 켬 / 끔"이다 — 단계 기본과 같은 값을 굳이 저장하면 나중에 기본이 바뀌어도 옛 값이
눌러앉아 "단계를 올렸는데 안 열리는" 사고가 난다.

### D3. 결제를 여는 방향만 검증한다 (fail-closed)

PortOne 설정이 준비되지 않았는데 단계만 올리면 사용자에게 결제 버튼이 보이는데 결제가 실패하는
최악의 상태가 된다. 그래서 결제가 새로 열리는 전이는 `GetPaymentReadinessUseCase`로 확인하고
준비되지 않았으면 **거부**한다(경고 아님). 반대로 **단계를 내리는 조치는 절대 막지 않는다** —
사고 대응 경로를 검증으로 막으면 안 된다.

### D4. 설정이 없으면 Stage 1로 fail-closed 한다

저장된 설정이 없을 때의 기본은 `BROWSE_ONLY`다. 이 단계만으로 신규 판매나 직거래 연결이 열리지는
않는다. 판매자 신원확인 래치(D7)가 별도로 준비된 경우에만 플랫폼이 돈을 만지지 않는 당근형
직거래를 시작한다. 운영자가 결제 준비 상태와 정산 모드를 확인하고 감사 사유를 남겨 명시적으로
단계를 올려야만 주문·결제가 열린다.

공개 설정 API 조회 자체가 실패한 클라이언트는 더 보수적인 Stage 0으로 닫는다. 즉 서버의
**미설정 기본값은 Stage 1**, 클라이언트의 **통신 실패 기본값은 Stage 0**이며 둘 다 결제를 열지 않는다.

### D5. 서버 자동 진단과 운영자 확인을 모두 통과해야 한다

환경변수만 채워졌다고 실제 영업 준비가 끝난 것은 아니다. Stage 2 이상은 다음 두 종류의 조건을
모두 통과해야 한다.

1. **자동 진단** — PortOne 결제 설정, 현재 정산 실행 모드, 현재 도메인·거래 모델에 대한 지급 계약
   확인값을 서버가 검사한다.
2. **운영 승인** — 서버가 판단할 수 없는 사업자 고지, 약관·개인정보, 결제·웹훅·환불 실거래,
   판매자 본인확인·계좌·지급 흐름을 관리자가 증빙과 대조해 확인한다.

운영 승인은 `launch_config.readiness`에 저장하고 확인·취소 사유와 조치자를 구조화 이력 및 관리자
감사 로그에 남긴다. Stage 2에는 `businessDisclosure`·`termsPrivacy`·`paymentFlow`가 필요하고,
Stage 3에는 `payoutFlow`까지 필요하다. 고단계에서 필수 확인을 취소하면 저장 단계도 Stage 1로
내려 결제가 환경 복구만으로 다시 열리지 않게 한다.

`businessDisclosure`는 사업자등록번호만 확인했다는 뜻이 아니다. **통신판매업 신고를 완료해 실제
신고번호를 교부받고**, 푸터·약관의 사업자 정보와 호스팅서비스 제공자, 공정거래위원회
사업자정보확인 링크에서 같은 정보를 확인한 뒤에만 승인한다. 현재 사용자에게서 통신판매업
신고번호를 제공받지 않았으므로 번호를 추정하거나 임시값으로 채우지 않으며, 플랫폼 주문·결제를
여는 Stage 2 전환 전에 반드시 아래 절차를 완료한다.

1. 관할 지방자치단체 또는 정부24에서 통신판매업 신고를 완료하고 신고번호를 확인한다.
2. 공정거래위원회 통신판매사업자 조회에 반영된 상호·대표자·주소·도메인이 실제 운영 정보와 같은지
   확인한다.
3. `BUSINESS_INFO`와 푸터·약관에 실제 신고번호를 추가하고, 초기 화면의 사업자정보 확인 링크가
   공정거래위원회 조회 화면으로 연결되는지 검증한다.
4. 변경 PR과 운영 증빙을 대조한 뒤에만 `businessDisclosure`를 승인한다.

확인된 카드에는 가장 최근 추가 전용 이력의 사유·조치자·시각을 다시 보여준다. 운영자가 현재
승인값의 근거를 찾기 위해 긴 이력 표를 역추적하지 않도록 하되, 원본은 별도 이력 컬렉션에 그대로
남긴다. 이력 보존 범위 밖의 과거 승인이라면 근거가 없다고 꾸미지 않고 명시적으로 안내한다.

이 확인값은 법률·세무 자문이나 PG 계약을 대신하지 않는다. 어드민은 운영자가 실제 증빙을 확인했다는
사실과 책임 추적 경로를 남기는 도구다.

### D6. 어드민은 공개 상태를 바꾸고, 실행 어댑터는 배포 설정으로 고정한다

어드민의 단계·기능 스위치는 사용자 노출과 서버 API 게이트를 배포 없이 바꾼다. 반면
`SETTLEMENT_MODE`와 PortOne 비밀값은 프로세스 부팅 시 선택되는 실행 어댑터이므로 어드민에서
즉석 변경하지 않는다. 비밀값·지급 구현을 웹 UI로 교체하면 설정 오입력 한 번이 실제 송금으로
이어질 수 있다. 실행 모드를 변경한 배포가 끝난 뒤 자동 진단과 운영 승인을 다시 확인하고 단계를
명시적으로 올린다.

### D7. 개인 판매자 신원확인은 출시 단계와 분리된 fail-closed 래치다

2026년 7월 21일 시행 전자상거래법 제20조의4는 개인 간 전자상거래를 중개하는 사업자에게 개인
판매자의 신원 확인 의무를 둔다. 하위 시행령 제25조의3은 중개 의뢰자가 개인인 경우 제공해야 할
정보 범위를 구체화한다. 현재 구현은 법적 의무를 완료했다고 선언하는 장치가 아니라, 준비되지 않은
판매를 열지 않기 위한 최소 기술 안전장치다.

- `GOLE_SELLER_IDENTITY_VERIFICATION_READY`는 기본 false이며 운영 Compose도 false로 고정한다.
  누락·구버전 API 응답·공개 설정 조회 실패는 모두 false로 해석한다.
- false인 동안 신규 매물 등록, 기존 listing의 새 Q&A·거래방 생성, 새 주문, listing 직거래 완료
  확인을 서버가 차단한다. 기존 공개 매물·Q&A 조회, 시세·커뮤니티·운영 문의, 이미 생성된 대화방
  재진입·메시지와 기존 확인 취소는 유지한다.
- true여도 대상 판매자의 `phoneNumber`와 `phoneVerifiedAt`이 실제 계정에 있어야 한다. 매물 등록은
  로그인 계정, 새 listing Q&A·거래방·주문·직거래 완료 확인은 요청자가 보낸 sellerId가 아니라
  서버가 매물 또는 listing 대화방에서 찾은 sellerId를 검사한다. legacy 온보딩 면제나 어드민 승인
  클릭으로 우회할 수 없다.
- 글로벌 미준비는 503 `SELLER_IDENTITY_VERIFICATION_UNAVAILABLE`, 판매자 계정 미인증은 403
  `SELLER_IDENTITY_VERIFICATION_REQUIRED`로 거부한다.
- 공개/관리자 launch 응답은 이 래치를 읽기 전용으로 보여준다. 관리 화면에는 변경 버튼을 두지
  않으며 배포 설정과 기존 활성 매물 사전 점검을 거쳐야만 바꾼다.

전화번호 OTP는 번호 소유 확인일 뿐 실명·주소 확인을 포함하지 않는다. 따라서 아래가 끝나기 전에는
운영 값을 true로 바꾸지 않는다.

1. 법 제20조의4와 시행령 제25조의3에 맞는 개인 판매자 정보 항목·확인 수단·증빙 보존 범위를
   법무 검토하고 개인정보처리방침에 반영한다.
2. 정해진 확인 수단을 계정별로 구현하고 테스트한다. 현재 `phoneVerifiedAt`만으로 법적 신원확인
   전체를 충족했다고 표시하지 않는다.
3. 운영 preflight에서 ACTIVE 매물의 판매자 중 확인 근거가 없는 매물 수가 0인지 PII 없이 확인한다.
4. 서버 503/403, 판매·상세·홈 준비중 화면과 운영 문의 링크를 검증한 배포에서만 래치를 연다.

### D8. 후기 운영 기준은 실제 코드와 같은 범위로 직접 공개한다

후기 기능이 열릴 때 작성 자격·게시기간·평점 기준과 표시 효과·공개 중단 기준·이의제기 경로를
`/review-policy`에 공개한다. 판매자 상점의 후기 영역과 전역 푸터에서 직접 연결한다. 현재 코드는
완료 주문의 구매자에게 주문당 1회, 1~5점과 1,000자 후기를 허용하고 숨김되지 않은 최신 100건을
최신순으로 공개·평점 계산한다. 이 범위를 넘어 영구 게시·검색 가중치·자동 제재가 있다고 쓰지 않는다.
후기 기능이 꺼져 있으면 신규 후기와 판매자 답글 POST를 모두 막고 기존 후기·평점 조회는 유지한다.

근거는 2026년 7월 21일 시행 법 제21조의4와 시행령 제27조의3이며, 후기 정책을 바꾸면 코드·정책
페이지·판매자 상점 직접 링크를 같은 배포에서 갱신한다.

### D9. 소비자 불만·분쟁 처리기준과 안내 목표를 공개·운영 화면에서 함께 관리한다

전자상거래법 시행령 제25조의2에 따라 불만·분쟁의 접수·조사·조치 기준을 `/terms`의
`#complaint-resolution-policy`에 공개한다. 신고 또는 운영 문의로 접수하고 플랫폼 기록과 당사자
제출 자료를 함께 검토하며, 결과에 따라 콘텐츠 공개 중단·계정 또는 거래 기능 제한·시정 안내를
적용하고 같은 문의 경로로 재검토를 받는다.

소비자에게는 접수 후 **3영업일 이내 진행 경과**, **10영업일 이내 조사 결과 또는 처리방안**을
알린다. `SupportTicket.progressDueAt`과 `responseDueAt`은 공휴일 달력을 임의로 구현하지 않고 각각
접수 후 72시간·240시간으로 더 이르게 잡는 내부 누락 방지 목표다. 사용자 응답과 관리자 인박스에
두 목표를 노출하지만, 이 값이 분쟁 자체의 자동 종결이나 법정 기한 충족을 증명한다고 표시하지
않는다. 실제 안내 메시지의 종류·시각을 구조화한 이행 원장은 별도 후속 과제로 남긴다.

## 프론트 계약 (고정)

`GET /api/v1/config/launch` — 인증 불필요.

```json
{
  "stage": 0,
  "tradeMode": "DIRECT_CHAT",
  "features": { "payments": false, "reviews": false, "partnerPayout": false },
  "sellerIdentityVerificationReady": false,
  "updatedAt": null
}
```

`stage`·`features`·`updatedAt` 은 프론트와 고정된 계약이라 빼거나 이름을 바꾸지 않는다. 필드
추가는 가능하다. 조회 실패 시 클라이언트는 Stage 0 으로 닫는다.

## 요구사항

- [x] R1. 단계(0~3)가 DB에 영속된다.

### T1. 직거래 완료가는 검증 전까지 시세 집계에서 제외한다 — 완료

**정책.** 직거래(`DIRECT_CHAT`)에서 신고된 거래완료가는 플랫폼이 결제를 매개하지 않아 금액을
검증할 수단이 없다. 양측이 합의만 하면 임의의 숫자를 넣을 수 있으므로, 그대로 집계하면 시세가
오염된다. 시세는 이 제품의 해자이므로 **검증되지 않은 체결가는 집계에 넣지 않는다.**

현재 체결가 기록은 `OrderService.complete` 의 `executedPriceRecorder.record(...)` 한 곳에서만
일어나고, 이 경로는 플랫폼 결제(2단계 이상)에서만 도달한다. 따라서 **지금은 오염이 없다.**
R9(거래완료 양측 확인)는 완료 사실과 매물 상태만 기록하고 임의 입력 가격을 체결가 파이프라인에
보내지 않는다.

**수용 기준** (R9 착수 시 함께 만족해야 함)

1. 체결가 레코드에 출처 구분이 있다 — 예: `source = PLATFORM_PAYMENT | DIRECT_TRADE`.
2. 시세 집계 쿼리가 기본적으로 `PLATFORM_PAYMENT` 만 읽는다. 직거래 건은 저장은 되되 집계에서 빠진다.
3. 테스트: 직거래 완료가를 넣어도 `GET /api/v1/prices/*` 의 통계(평균·중앙값·거래량)가 변하지 않는다.
4. 테스트: 플랫폼 결제 완료가는 기존과 동일하게 집계에 반영된다(회귀 방지).
5. 직거래 건을 집계에 포함하는 별도 스위치를 둔다면, 기본값은 **제외**이고 변경은 이 스펙의
   변경 이력에 남는다.

구현 근거: `PriceTransactionSource`, `MarketEvidencePolicy`, 주문 ID 기반
`sourceReference`, `PricingServiceTest.marketReadsExcludeDirectDemoAndUnverifiedEvidenceByDefault`.
콜드스타트 표시 계약은 `.kiro/specs/pricing-evidence/spec.md`에서 이어 간다.
