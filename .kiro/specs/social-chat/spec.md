# 소셜 채팅 (social-chat)

## 왜 필요한가

지금 채팅은 매물에 종속돼 있다. `ChatRoom`은 `listingId`·`buyerId`·`sellerId`를 필수로 요구하고
(`chat/domain/model/ChatRoom.java`), 방을 만드는 유일한 경로가 "이 매물에 대해 판매자에게 말 걸기"다.
그래서 매물과 무관한 대화 — 사용자끼리의 잡담, 여러 명이 모이는 방, 운영팀 문의 — 는 표현할 방법이
아예 없다.

이 스펙은 채팅을 **독립 소셜 도메인**으로 올린다. 매물 대화는 그중 한 종류가 된다.

## 결정

### D0. 운영 문의는 분류와 권리 요청 응답 목표를 가진다

`SUPPORT`는 일반·거래·결제·제품 피드백뿐 아니라 개인정보 열람·정정·삭제·처리정지 요청을
구조화해 받는다. 개인정보 권리 요청의 상세 운영 규칙은
[`privacy-rights-operations`](../privacy-rights-operations/spec.md)를 따른다.

### D1. 방 유형은 네 가지, 권한 규칙이 유형마다 다르다

| 유형      | 구성                         | 생성 주체            | 특징                                      |
| --------- | ---------------------------- | -------------------- | ----------------------------------------- |
| `DIRECT`  | 사용자 2명                   | 누구나               | 같은 상대와는 항상 같은 방(멱등)          |
| `GROUP`   | 3명 이상                     | 누구나               | 방장·제목, 초대·나가기                    |
| `LISTING` | buyer + seller + `listingId` | 매물 문의            | **직거래 완료 확인이 가능한 유일한 유형** |
| `SUPPORT` | 사용자 1명 + 배정된 운영자   | 로그인 사용자 누구나 | 배정·상태·내부 메모                       |

유형을 필드 하나로 두고 규칙을 분기하는 이유는, 규칙이 다른 것을 같은 자료구조로 뭉개면
"이 방에서 직거래 완료를 눌러도 되나"를 호출부마다 다시 판단하게 되기 때문이다. 판단은
도메인 한 곳(`ChatRoomType`)에 둔다.

### D2. 직거래 완료 확인은 `LISTING`에서만

직거래 완료 확인은 _어떤 매물의_ 거래가 끝났다는 선언이다. `listingId`가 없는 방에서는 무엇이
완료됐는지 지목할 대상이 없고, 완료가는 시세 집계 후보가 되므로(`launch-stage` T1) 대상 없는
완료는 데이터 오염이다. `DIRECT`/`GROUP`/`SUPPORT`에서의 완료 확인 시도는 도메인에서 거부한다.

### D3. DIRECT 멱등은 정렬된 참여자 키로

같은 두 사람이 여러 번 "대화 시작"을 눌러도 방은 하나여야 한다. 참여자 id를 정렬해 만든
`dedupeKey = "DIRECT:" + min(a,b) + ":" + max(a,b)` 에 unique 인덱스를 걸고, 생성은
`조회 → 없으면 insert → duplicate key면 재조회` 로 처리한다. 정렬하지 않으면 (a,b)와 (b,a)가
다른 키가 되어 두 방이 생긴다.

자기 자신과의 DM은 금지한다. `dedupeKey`가 `DIRECT:x:x`가 되어 형식상으론 만들어지지만,
"상대가 없는 대화"는 읽음·안 읽음도 신고도 의미가 없다.

### D4. 차단은 양방향으로 막는다

차단은 새 도메인이다(현재 저장소에 차단 기능이 없다). A가 B를 차단하면 **누가 시도하든**
A↔B의 새 `DIRECT` 방 생성과 메시지 전송이 막힌다. 한쪽 방향만 막으면 차단한 사람이 차단당한
사람에게 계속 말을 걸 수 있어, 차단이 "안 보기"가 아니라 "일방적 확성기"가 된다.

이미 있는 방은 지우지 않는다 — 과거 대화는 신고·분쟁의 증거이므로 보존하고 전송만 막는다.

공동 `GROUP`에서는 한 사람의 차단으로 다른 멤버 전체의 대화를 멈추지 않는다. 차단 관계가 새
그룹 생성·초대되는 것은 거부하고, 이미 함께 있던 그룹에서는 차단한 사용자 화면에 대상 메시지를
접어 숨긴다. 필요하면 그룹을 나갈 수 있다.

### D5. 관리자는 SUPPORT 밖에서 대화를 볼 수 없다

관리자 권한은 운영 조치를 위한 것이지 사생활 열람권이 아니다.

- `SUPPORT` — 배정된 관리자는 정식 멤버다. 읽고 답한다.
- `DIRECT`/`GROUP`/`LISTING` — 관리자도 **멤버가 아니면 읽지 못하고, 어떤 경우에도 보내지 못한다.**

긴급 신고로 열람이 필요한 경우는 D6의 절차를 거친다. "관리자니까 볼 수 있다"는 경로는 만들지 않는다.

### D6. 신고 열람은 스냅샷 + 감사로만

채팅 신고가 들어오면 관리자는 대화 원본을 실시간으로 뒤지는 대신 **신고 시점에 고정된 스냅샷**을
본다.

1. 신고 접수 시 대상 메시지와 앞뒤 문맥을 `chat_report_snapshots`에 복사한다(추가 전용).
2. 스냅샷 열람은 `ORDER_CONTACT_VIEW`와 같은 급으로 감사 로그에 남긴다 — 열람 자체가 조치다.
3. 관리자는 스냅샷을 통해서만 본다. 살아 있는 방에 대한 읽기 권한은 부여되지 않는다.
4. 스냅샷은 신고가 종결돼도 보존 정책에 따라 남는다(대화 삭제가 증거를 지우지 못하게).

실시간 열람 대신 스냅샷인 이유: 실시간 접근권을 한 번 만들면 그 권한은 신고와 무관한 대화에도
쓸 수 있게 된다. 스냅샷은 볼 수 있는 범위가 신고 대상으로 물리적으로 제한된다.

### D7. SUPPORT 인박스는 상태 기계다

`UNASSIGNED`(미배정) → `IN_PROGRESS`(진행중) → `WAITING_USER`(답변대기) → `RESOLVED`(완료).

- 배정: 관리자가 자기에게 가져간다(`UNASSIGNED` → `IN_PROGRESS`).
- 이관: 다른 관리자에게 넘긴다. 담당자만 바뀌고 상태는 유지된다.
- 답변: 관리자 메시지 전송 시 `IN_PROGRESS` → `WAITING_USER`.
- 사용자 응답: 사용자 메시지 전송 시 `WAITING_USER` → `IN_PROGRESS` (다시 우리 차례).
- 완료/재개: `RESOLVED` ↔ `IN_PROGRESS`.

배정·이관·상태 변경·관리자 답변은 **전부** 감사 로그에 남는다. 문의 처리는 개인정보를 다루는
일이라 누가 언제 무엇을 했는지가 사후에 필요하다.

### D8. 내부 메모는 사용자에게 절대 가지 않는다

내부 메모는 `chat_messages`에 넣지 않고 **별도 컬렉션** `support_internal_notes`에 둔다.
같은 컬렉션에 플래그로 구분하면, 언젠가 플래그 조건을 빠뜨린 쿼리 하나가 사용자에게 내부 메모를
노출시킨다. 자료 구조를 분리하면 그 실수가 불가능해진다 — 사용자 메시지 조회 경로는 메모
컬렉션을 아예 모른다.

### D9. 읽음은 방마다 `(sentAt, messageId)` 커서 하나로 관리한다

네 방 유형은 메시지 컬렉션을 공유하므로 읽음 계약도 하나만 둔다. 커서는 단순한 메시지 ID가 아니라
`lastReadSentAt + lastReadMessageId` 쌍이다. 같은 시각에 여러 메시지가 저장돼도 Mongo와 웹이 사용하는
정렬 `(sentAt, _id)`를 그대로 따라야 누락이 없다.

- 안 읽음은 **현재 읽을 수 있는 방**에서 상대가 보낸 커서 이후 메시지 수다. 본인 메시지는 세지 않는다.
- 읽음 처리는 `requireReadable`을 먼저 통과하고, 요청한 메시지가 같은 방에 속하는지 확인한 뒤 수행한다.
- 커서는 Mongo 조건부 갱신으로 앞으로만 이동한다. 느린 이전 요청이 새 커서를 되돌릴 수 없다.
- `SUPPORT`는 방의 오래된 멤버 배열이 아니라 티켓의 현재 문의자·담당자를 다시 검사한다.
- 새 그룹 멤버는 과거 이력을 볼 수 있지만 초대 시점 이전 메시지는 안 읽음으로 세지 않는다. 초대 직후
  당시 말단으로 커서를 초기화하며, 이미 있는 멤버를 다시 초대하는 멱등 요청은 기존 커서를 바꾸지 않는다.

API는 `GET /api/v1/chat/unread-counts`와
`POST /api/v1/chat/rooms/{roomId}/read { lastMessageId }`로 통합한다. 방 목록의 기존 10초 폴링에
카운트를 합치고, 실제 대화 패널이 보이는 동안 서버가 읽음을 확정한 뒤에만 배지를 지운다.

## 기존 `chat_rooms` 무중단 호환

### 호환 규칙

1. 기존 매물 대화는 `chat_rooms`에 그대로 둔다. `buyerId + sellerId + listingId` unique 인덱스와
   주문·직거래 동선도 바꾸지 않는다.
2. `DIRECT`·`GROUP`·`SUPPORT`는 `social_chat_rooms`에 저장한다. 이 컬렉션은
   `dedupeKey` sparse unique 인덱스와 `memberIds + lastMessageAt` 활동 인덱스를 독립적으로 가진다.
3. `MongoSocialChatRoomAdapter`가 두 컬렉션을 하나의 읽기 포트로 합친다. 응용 계층과 웹은 방이
   어느 컬렉션에 있는지 알 필요가 없다.
4. 메시지는 두 방 유형 모두 기존 `chat_messages`를 공유한다. `roomId` 접근 검사는 통합 포트를
   거치므로 비멤버·이전 지원 담당자에게 이력이 새지 않는다.
5. 별도 컬렉션을 택했으므로 운영 DB의 기존 unique 인덱스를 드롭하지 않고도 무중단 배포할 수 있다.

### 왜 별도 컬렉션인가

`chat_rooms`의 세 필드 unique 인덱스는 필드가 없는 문서를 모두 같은 `null + null + null`로
취급한다. 여기에 소셜 방을 함께 넣으면 두 번째 방부터 중복 키로 실패하고, partial 인덱스로
바꾸려면 배포 중 운영 인덱스를 삭제·재생성해야 한다. 지금 단계에서는 데이터 마이그레이션 없이
안전하게 여는 것이 더 중요하므로 물리 저장만 분리하고 포트에서 논리적으로 통합한다.

## 요구사항

- [x] R1. 방 유형 `DIRECT`/`GROUP`/`LISTING`/`SUPPORT` 구분.
- [x] R2. 누구나 다른 사용자와 1:1 방을 만들 수 있다.
- [x] R3. 같은 상대와의 DM은 몇 번 요청해도 한 방이다(멱등).
- [x] R4. 자기 자신과의 DM은 거부된다(`CHAT_SELF_DM`).
- [x] R5. 그룹 초대·나가기. 방장이 나가면 가장 오래된 잔여 멤버에게 승계하고, 남는 사람이 없으면 방을 닫는다.
- [x] R6. 멤버만 조회·전송한다(`CHAT_NOT_A_MEMBER`).
- [x] R7. 차단된 상대와는 1:1 방 생성·전송이 양방향으로 막히고(`CHAT_BLOCKED`), 공동 그룹의 대상 메시지는 차단자에게 숨겨진다.
- [x] R8. 채팅 신고가 대상 메시지 스냅샷과 함께 접수된다.
- [x] R9. 기존 `chat_rooms` 문서가 마이그레이션 없이 그대로 읽힌다.
- [x] R10. 직거래 완료 확인은 `LISTING` 방에서만 허용된다(`CHAT_DIRECT_TRADE_NOT_ALLOWED`).
- [x] R11. 모든 로그인 사용자가 SUPPORT 방을 만들 수 있다.
- [x] R12. ADMIN 인박스: 상태 필터(미배정·진행중·답변대기·완료), 자기 배정, 답변, 이관, 완료/재개.
- [x] R13. 내부 메모는 사용자 조회 경로에 절대 나타나지 않는다.
- [x] R14. 배정·이관·상태 변경·관리자 답변이 감사 로그에 남는다.
- [x] R15. 관리자는 SUPPORT 밖의 방을 읽지 못하고 어떤 방에도 비멤버로 전송하지 못한다.
- [x] R16. 신고 열람은 스냅샷 경유이며 열람이 감사에 남는다.
- [x] R17. 모든 방 유형의 안 읽음 수를 한 API에서 조회하고 현재 권한을 다시 검사한다.
- [x] R18. 읽음 커서는 `(sentAt, messageId)` 기준으로 원자적·멱등하게 전진하며 역행하지 않는다.
- [x] R19. 모바일 목록 진입만으로 읽음 처리하지 않고, 방을 실제로 열어 서버가 확정한 뒤 배지를 지운다.
- [x] R20. 새 그룹 멤버에게 초대 이전 이력이 안 읽음 폭탄으로 표시되지 않는다.
- [x] R21. 직거래 완료 확인은 별도 대화상자로 결과를 명시하고 재확인한다. 한쪽이 먼저 확인한
      두 번째 확인은 되돌릴 수 없는 판매 완료임을 구분해 알리며, 완료 전 확인 취소는 즉시 처리한다.

## 수용 기준 (테스트로 고정할 것)

**권한**

- 비멤버 사용자가 방을 조회·전송하면 403이고, ADMIN이어도 `DIRECT`/`GROUP`/`LISTING`에서 동일하다.
- 배정된 관리자는 자기 `SUPPORT` 방을 읽고 답할 수 있다. 배정되지 않은 관리자는 인박스 목록은
  보되 대화 본문은 배정 후에 본다.

**멱등·중복**

- 같은 두 사용자로 DM 생성을 100회 동시 호출해도 방은 1개다(동시성 테스트).
- 자기 자신과의 DM은 거부된다.

**차단**

- A가 B를 차단한 뒤: B→A DM 생성 실패, A→B DM 생성 실패, 기존 방에서 양방향 전송 실패, 과거
  메시지 조회는 성공(보존).

**호환**

- `type`·`memberIds`가 없는 레거시 문서를 넣고 조회하면 `LISTING`으로 읽히고 멤버는
  `[buyerId, sellerId]`다.
- 레거시 문서에 대해 기존 매물 채팅 동선(문의·전송·직거래 완료 확인)이 그대로 동작한다.

**직거래**

- `LISTING`이 아닌 방에서 완료 확인을 시도하면 거부된다.
- `거래 완료`를 누르면 API 호출 전 확인 대화상자가 열리고, 취소·Escape에는 호출하지 않으며
  명시적인 확인 뒤에만 호출한다. 상대방이 먼저 확인한 경우에는 최종 판매 완료임을 별도로 알린다.
- 양쪽이 동시에 오래된 방 상태를 보고 눌러도 확인 대화상자를 우회할 수 없다.
- 양측 확인 완료는 보조 기술이 즉시 알 수 있도록 live status로 알린다.

**SUPPORT**

- 상태 전이가 D7 표대로만 일어난다. 관리자 답변이 `WAITING_USER`로, 사용자 응답이 `IN_PROGRESS`로 되돌린다.
- 내부 메모를 남긴 뒤 **사용자 메시지 조회 응답에 그 문자열이 없다**(직렬화 결과를 문자열로 단정).
- 배정·이관·완료·재개·관리자 답변마다 감사 레코드가 1건씩 쌓인다.

**읽음·안 읽음**

- 커서 없음 → 상대 메시지만 모두 안 읽음이며 본인 메시지는 제외된다.
- 같은 시각 메시지는 ID 순서를 함께 비교하고, 최신 커서 뒤 늦게 도착한 과거 읽음 요청은 무시된다.
- 다른 방 메시지 ID로 읽음 처리하면 `CHAT_READ_CURSOR_INVALID`다.
- 이전 SUPPORT 담당자는 방 멤버 배열에 남아 있어도 안 읽음 조회·읽음 처리 모두 허용되지 않는다.
- 모바일에서 방 목록만 열 때 읽음 POST가 없고, 방 선택 뒤 성공한 POST만 해당 배지를 0으로 만든다.

## 구현 상태

도메인·Mongo 저장·웹 API·관리자 지원 인박스·사용자 채팅 UI가 연결돼 있다. DIRECT 생성 100건
동시 호출이 단일 방으로 수렴하는 통합 테스트와 레거시 `chat_rooms` 무마이그레이션 읽기 테스트를
포함한다. 브라우저 E2E는 방 생성·그룹·차단·읽음·직거래 완료 확인 동선을 고정한다.
