# 운영자 콘솔 (Admin Console) — 요구사항

> 형식: EARS (Easy Approach to Requirements Syntax).
> 선행 스펙: `.kiro/specs/admin-and-payments/` (인증 세션·RBAC·최초 관리자 API).
> 본 스펙은 그 후속으로 **"같은 사이트에서 관리자 계정으로 로그인하면 운영 기능이 열리는"** 통합 운영자 콘솔을 정의한다.

## 0. 개요

### 문제

1. **별도 어드민이 아니다.** 운영자는 gole.co.kr 에 자기 계정으로 로그인한다. 별도 도메인·별도 앱·별도 로그인은 만들지 않는다. 권한(ADMIN)이 곧 기능 노출 조건이다.
2. **관리 기능이 한 페이지에 뭉쳐 있다.** `/admin` 단일 화면에 현황·주문·신고·매물·게시글·회원·카탈로그가 모두 세로로 쌓여 있어 운영 작업 동선이 없다.
3. **모더레이션이 도메인을 우회한다.** 게시글 삭제·회원 잠금이 `AdminController`에서 `MongoTemplate`로 컬렉션을 직접 수정한다. 헥사고날 규약(NFR-3) 위반이며 도메인 불변식을 건너뛴다.
4. **정지가 실효성이 없다.** 회원 잠금은 `lockedUntil`을 9999년으로 세팅하는 편법이다. 이미 발급된 세션 토큰(TTL 7일)은 그대로 살아 있어, 잠긴 사용자가 계속 글을 쓰고 매물을 올릴 수 있다.
5. **감사 추적이 없다.** 누가·언제·무엇을·왜 조치했는지 남지 않는다. 운영 분쟁 시 근거가 없다.

### 용어

| 용어 | 의미 |
|---|---|
| 운영자(ADMIN) | `role = ADMIN` 계정. 일반 사용자와 **같은 로그인·같은 사이트**를 쓴다. |
| 콘솔 | `/admin/**` 운영 화면 묶음. |
| 온사이트 어드민 모드 | 일반 화면(매물 상세, 커뮤니티 글)에서 운영자에게만 노출되는 인라인 조치 UI. |
| 조치(admin action) | 상태를 바꾸는 운영 행위. 전량 감사 로그 대상. |
| 정지(SUSPENDED) | 운영자가 계정을 비활성화한 상태. 로그인 및 기존 세션 모두 차단. |

## 요구사항 1 — 권한 게이트와 진입 (같은 사이트·같은 로그인)

**사용자 스토리:** 운영자로서, 평소 쓰던 사이트에 내 계정으로 로그인하는 것만으로 운영 기능을 쓰고 싶다.

#### 수용 기준
- 1.1 WHEN ADMIN 계정으로 로그인하면, 시스템은 별도 인증 절차 없이 헤더에 콘솔 진입점을 노출해야 한다.
- 1.2 IF 요청자가 ADMIN이 아니면, 시스템은 `/api/admin/**` 전 요청을 거부해야 한다(비로그인·만료 401 `INVALID_SESSION`, USER 403 `ADMIN_ONLY`).
- 1.3 IF 비로그인 사용자가 `/admin/**`에 접근하면, 시스템은 로그인 안내를 표시해야 한다.
- 1.4 IF USER 권한 사용자가 `/admin/**`에 접근하면, 시스템은 접근 권한 없음 안내를 표시해야 하며 운영 데이터를 노출하지 않아야 한다.
- 1.5 시스템은 `/admin/**` 전 경로에 `noindex, nofollow`를 적용해야 한다.
- 1.6 WHEN ADMIN이 일반 화면(매물 상세·커뮤니티 글)을 열면, 시스템은 해당 화면에서 바로 조치할 수 있는 인라인 운영 UI를 노출해야 한다. (온사이트 어드민 모드)
- 1.7 IF 사용자가 ADMIN이 아니면, 시스템은 온사이트 어드민 모드를 렌더링하지 않아야 한다.

## 요구사항 2 — 콘솔 정보구조(IA)와 대시보드

**사용자 스토리:** 운영자로서, 오늘 처리할 일이 무엇인지 한눈에 보고 해당 화면으로 바로 이동하고 싶다.

#### 수용 기준
- 2.1 시스템은 콘솔을 다음 섹션으로 분리하고 좌측 내비게이션으로 이동할 수 있어야 한다: 대시보드(`/admin`), 신고(`/admin/reports`), 매물(`/admin/listings`), 주문(`/admin/orders`), 커뮤니티(`/admin/community`), 회원(`/admin/accounts`), 카탈로그(`/admin/catalog`), 감사 로그(`/admin/audit`).
- 2.2 WHEN 대시보드를 열면, 시스템은 컬렉션별 도큐먼트 수, 완료 주문 기준 거래액(GMV), 주문 상태별 건수, 활성 매물 수를 반환·표시해야 한다.
- 2.3 WHEN 미처리(PENDING) 신고가 있으면, 시스템은 내비게이션과 대시보드에 미처리 건수 뱃지를 표시해야 한다.
- 2.4 WHEN 대시보드를 열면, 시스템은 최근 관리자 조치 이력을 요약 표시해야 한다.
- 2.5 콘솔의 모든 목록은 조회 시점 데이터를 사용해야 하며(캐시 금지, `no-store`), 조치 후에는 해당 목록을 갱신해야 한다.

## 요구사항 3 — 신고 큐 (notice & takedown)

**사용자 스토리:** 운영자로서, 접수된 신고를 상태별로 확인하고 대상 콘텐츠를 확인한 뒤 조치하거나 기각하고 싶다.

#### 수용 기준
- 3.1 WHEN 운영자가 신고 목록을 요청하면, 시스템은 상태(`PENDING`/`RESOLVED`/`DISMISSED`) 필터와 건수 제한(기본 30, 최대 100)을 적용해 반환해야 한다.
- 3.2 시스템은 신고 행에서 대상(매물/게시글) 상세 화면으로 이동할 수 있는 링크를 제공해야 한다.
- 3.3 WHEN 운영자가 신고를 조치완료 처리하면, 시스템은 신고를 `RESOLVED`로 전이해야 한다.
- 3.4 WHEN 운영자가 신고를 기각하면, 시스템은 신고를 `DISMISSED`로 전이해야 한다.
- 3.5 IF 이미 처리된 신고를 다시 처리하려 하면, 시스템은 `REPORT_ALREADY_HANDLED`로 거부해야 한다.
- 3.6 WHEN 신고를 조치완료 처리하면, 시스템은 감사 로그를 남겨야 한다(요구사항 8).

## 요구사항 4 — 매물 모더레이션

**사용자 스토리:** 운영자로서, 가품·도용·허위 매물을 즉시 내리고 그 사유를 남기고 싶다.

#### 수용 기준
- 4.1 WHEN 운영자가 매물 목록을 요청하면, 시스템은 상태 무관 최근순 목록을 반환해야 한다(일반 검색과 달리 `DELETED` 포함).
- 4.2 WHEN 운영자가 매물 강제 내림을 요청하면, 시스템은 사유(reason)를 필수로 받아 매물을 `DELETED`로 전이해야 한다.
- 4.3 IF 매물에 진행 중 주문이 있어도, 운영자 강제 내림은 **성공해야 한다**. (일반 셀러 삭제와 달리 모더레이션은 도메인 차단 규칙보다 우선한다. 진행 중 주문의 정산은 주문 컨텍스트에서 별도 처리한다.)
- 4.4 IF 이미 `DELETED`인 매물을 다시 내리면, 시스템은 멱등하게 성공 처리해야 한다.
- 4.5 WHEN 매물을 내리면, 시스템은 감사 로그를 남겨야 한다.
- 4.6 WHEN ADMIN이 매물 상세 화면을 보면, 시스템은 그 화면에서 바로 내림 조치를 할 수 있어야 한다(요구사항 1.6).

## 요구사항 5 — 커뮤니티 모더레이션

**사용자 스토리:** 운영자로서, 부적절한 게시글을 작성자 확인 없이 내리고 사유를 남기고 싶다.

#### 수용 기준
- 5.1 WHEN 운영자가 게시글 목록을 요청하면, 시스템은 상태 무관 최근순 목록을 반환해야 한다.
- 5.2 WHEN 운영자가 게시글 삭제를 요청하면, 시스템은 작성자 검증을 생략하고(운영자 오버라이드) 사유를 받아 게시글을 `DELETED`로 전이해야 한다.
- 5.3 시스템은 이 전이를 커뮤니티 컨텍스트의 **인바운드 포트를 통해** 수행해야 하며, 관리자 컨텍스트가 `posts` 컬렉션을 직접 수정하지 않아야 한다(NFR-3).
- 5.4 IF 존재하지 않는 게시글이면, 시스템은 404 `POST_NOT_FOUND`를 반환해야 한다.
- 5.5 WHEN 게시글을 내리면, 시스템은 감사 로그를 남겨야 한다.
- 5.6 WHEN ADMIN이 커뮤니티 글 상세를 보면, 시스템은 그 화면에서 바로 삭제 조치를 할 수 있어야 한다(요구사항 1.6).

## 요구사항 6 — 회원 관리 (정지 / 복구 / 권한)

**사용자 스토리:** 운영자로서, 사기·악성 이용자의 계정을 즉시 정지시켜 더 이상 거래·게시를 못 하게 하고 싶다.

#### 수용 기준
- 6.1 WHEN 운영자가 회원 목록을 요청하면, 시스템은 이메일 부분 일치 검색과 건수 제한을 적용해 (id, email, role, status, lockedUntil, 정지 사유)를 반환해야 한다.
- 6.2 WHEN 운영자가 계정 정지를 요청하면, 시스템은 사유를 받아 계정을 `SUSPENDED`로 전이해야 한다.
- 6.3 WHEN 계정이 `SUSPENDED`로 전이되면, 시스템은 **해당 계정의 모든 활성 세션을 즉시 폐기**해야 한다.
- 6.4 IF `SUSPENDED` 계정이 로그인을 시도하면, 시스템은 403 `ACCOUNT_SUSPENDED`로 거부해야 한다.
- 6.5 IF `SUSPENDED` 계정의 기존 토큰으로 API를 호출하면, 시스템은 세션 해석을 실패시켜 401을 반환해야 한다(세션 폐기 누락 시의 2차 방어선).
- 6.6 WHEN 운영자가 정지를 해제하면, 시스템은 계정을 `VERIFIED`로 복구하고 로그인 실패 카운터·잠금을 초기화해야 한다.
- 6.7 WHEN 운영자가 계정 권한을 변경하면, 시스템은 role을 갱신하고 해당 계정의 세션을 폐기해 새 권한으로 재로그인하게 해야 한다.
- 6.8 IF 운영자가 **자기 자신**을 정지하거나 자기 권한을 강등하려 하면, 시스템은 400 `ADMIN_SELF_TARGET`으로 거부해야 한다.
- 6.9 IF 대상이 마지막 남은 ADMIN이면, 시스템은 정지·강등을 400 `LAST_ADMIN`으로 거부해야 한다.
- 6.10 WHEN 회원 상태·권한을 변경하면, 시스템은 감사 로그를 남겨야 한다.

## 요구사항 7 — 주문 모니터링 / 카탈로그 관리

**사용자 스토리:** 운영자로서, 거래 흐름을 모니터링하고 카탈로그 기준 정보를 관리하고 싶다.

#### 수용 기준
- 7.1 WHEN 운영자가 주문 목록을 요청하면, 시스템은 상태 필터를 적용해 최근순으로 반환해야 한다(읽기 전용).
- 7.2 WHEN 운영자가 카탈로그 세트를 등록하면, 시스템은 세트를 추가하고 201로 응답해야 한다.
- 7.3 WHEN 운영자가 기존 세트를 수정하면, 시스템은 세트 정보를 갱신해야 한다.
- 7.4 WHEN 운영자가 세트의 홈 추천(featured) 여부를 토글하면, 시스템은 해당 플래그만 갱신해야 한다.
- 7.5 WHEN 카탈로그를 변경하면, 시스템은 감사 로그를 남겨야 한다.

## 요구사항 8 — 감사 로그 (Audit Log)

**사용자 스토리:** 운영자로서, 어떤 운영자가 언제 무엇을 왜 조치했는지 추적해 분쟁에 대응하고 싶다.

#### 수용 기준
- 8.1 WHEN 상태를 바꾸는 관리자 조치가 성공하면, 시스템은 (조치자 id·이메일, 조치 유형, 대상 유형·id, 사유, 시각)을 감사 로그로 기록해야 한다.
- 8.2 시스템은 조치가 **성공한 경우에만** 기록해야 한다(실패·거부는 기록하지 않는다).
- 8.3 WHEN 운영자가 감사 로그를 조회하면, 시스템은 최근순 목록을 건수 제한과 함께 반환해야 한다.
- 8.4 시스템은 감사 로그에 대한 수정·삭제 API를 제공하지 않아야 한다(append-only).
- 8.5 IF 감사 기록에 실패하더라도, 시스템은 이미 성공한 본 조치를 롤백하지 않아야 한다(감사 실패가 운영을 막지 않는다).
- 8.6 감사 로그 조회는 ADMIN 전용이어야 한다.

## 요구사항 9 — 아키텍처 준수 (NFR)

- 9.1 관리자 컨텍스트는 다른 컨텍스트의 **인바운드 포트(UseCase)에만** 의존해야 하며, 타 컨텍스트의 서비스·어댑터·컬렉션을 직접 참조하지 않아야 한다.
- 9.2 운영 리포팅용 **읽기 전용 조회**는 관리자 컨텍스트의 아웃바운드 포트(`AdminReadModelPort`)로 추상화하고, MongoDB 접근은 어댑터에 격리해야 한다. 컨트롤러는 `MongoTemplate`를 직접 참조하지 않아야 한다.
- 9.3 프론트엔드는 FSD 레이어 규칙(app→views→widgets→features→entities→shared)을 위반하지 않아야 한다.
- 9.4 관리자 조치 API는 모두 `POST`여야 하며(멱등 GET 금지), 목록 조회의 `limit`은 서버에서 1~100으로 클램프해야 한다.

## 비범위

- 관리자 2FA / IP 허용목록 — 후속.
- 주문 강제 환불·강제 완료(운영자 개입 정산) — 후속. 현재는 읽기 전용 모니터링.
- 신고 자동 분류·머신러닝 스코어링 — 후속.
- 감사 로그 외부 반출(SIEM 연동) — 후속.
- 관리자 권한 세분화(모더레이터/정산담당 등 역할 분리) — 후속. 현재는 USER/ADMIN 2단계.

## 보안 고려

- 정지된 계정은 **로그인 차단 + 기존 세션 폐기 + 세션 해석 거부** 3중으로 막는다. (6.3~6.5)
- 마지막 ADMIN 강등·정지 차단으로 운영 잠금(lockout)을 방지한다. (6.9)
- 자기 자신 대상 조치를 차단해 실수로 인한 권한 상실을 방지한다. (6.8)
- 감사 로그는 append-only. 조치자 이메일을 스냅샷으로 함께 저장해 계정 삭제 후에도 추적 가능하게 한다.
