# 홍보 에이전트 초안 품질 평가 v1

## 목적과 적용 범위

최우선 목표는 **사람이 안심하고 검토할 만한 초안**이다. 조회수·발행량·모델 실행 성공을
초안 품질의 대리 지표로 사용하지 않는다. 평가는 승인이나 발행 권한을 부여하지 않는다.
두 분류 모두 사람이 검토·승인하고 별도로 발행한다.

2026-09-18 사용자 합의:

- 페르소나: 레고 취향을 공유하며 작은 개선을 보여주고 가끔 의견을 묻는 개발팀.
- 담백한 기능 설명, 취향과 가벼운 농담, 대화형 질문을 목적에 맞게 섞는다.
- 계정 페르소나를 위한 약간의 창작을 허용한다.
- `일일 홍보`와 `릴리스 소식`은 관리자 화면의 분류이며 외부 해시태그가 아니다.

현재 PR #135는 릴리스 후보 탐색·촬영·캡션 생성·검토 요청까지 구현한다.
일일 홍보 생성과 관리자 분류 필드는 후속이며, 여기의 분류는 우선 평가 기록에만 사용한다.
이 문서는 수동 평가 프로토콜이다. 자동 채점기·계측·생성 프롬프트 변경은 포함하지 않는다.

## 평가 단위와 증거

평가 단위는 `case_id × 실행 버전 × attempt_id`다. 첫 시도를 주 지표로 삼고, 재시도는 별도
기록한다. 여러 결과 중 좋은 것만 골라 첫 시도처럼 집계하지 않는다.

입력에는 후보 SHA, diff, 촬영 대상 버전·환경, 공개 가능 화면, 최근 글과 반려 이력,
현재 이용 가능한 기능을 확인할 자료를 고정한다. 소스에 구현됐다는 이유만으로 운영에서
사용할 수 있다고 판정하지 않는다. 버전이 다른 화면이나 비활성 기능은 명시한다.
근거가 부족하면 `판정 보류`이며 정확하다고 추정하지 않는다.

원본 캡션·선택한 이미지 순서·최종 수정본을 구분해 보관한다. 민감한 이미지·이용자 원문은
저장소에 커밋하지 않고 접근 제한된 증거 위치만 기록한다. 보관 위치·접근권한·만료일을
평가 시작 전에 정하며, 현재 실행 세션의 기본 보존 7일이 평가 증거의 영구 보존을 뜻하지 않는다.

## 창작 허용 기준

아래는 사용자 합의를 평가 가능하게 구체화한 v1 운영안이다. 최초 평가에서 팀이 함께 보정한다.

| 표현 | 판정 기준 |
|---|---|
| 비유·농담·가벼운 감정 | 허용. 예: “둘 자리는 아직 못 만들어줬어” |
| 커피·야근 등 사소한 개발 일화 | 창작이라는 이유만으로 감점하지 않음. 평가 기록에 해당 문구를 표시하고 검토자가 유지 여부 결정 |
| 기능·출시·가격·거래 안전성·이용자 수·후기 | 사실 주장으로 취급하며 근거 필수. 페르소나 창작으로 면제하지 않음 |
| 개발 일화에 섞인 제품 사실 | 분리 평가. “커피 세 잔 마시고 결제 오류를 고쳤어”에서 오류와 수정 여부는 근거 필요 |
| 향후 기능 질문 | 질문은 허용하되 제공 중이거나 출시가 확정된 것처럼 쓰면 사실 오류 |

창작 표시는 평가 기록용이다. 관리자 UI에 표시하는 기능은 아직 없으며 외부 게시문에
일괄 표시하는 정책도 확정하지 않았다. 실제 개인의 발언·행동을 임의로 만들어 넣지 않는다.

## 건별 평가

### 먼저 확인하는 보류 조건

다음 중 하나라도 있으면 점수 합계와 관계없이 `보류`한다. 이유와 문제 문구/이미지를 남긴다.

- 근거와 충돌하거나 근거 없이 단정한 중요한 제품 사실: 미출시 기능, 결제·가격·안전성 등.
- 개인정보·인증정보·비공개 정보 노출 또는 다른 이용자의 자료를 홍보에 사용할 수 있는지 미확인.
- 실제로 하지 않은 이용자 후기·사용 실적·제휴를 지어냄.
- 게시 가능 여부를 판단할 핵심 증거가 없음. 이 경우는 확정 결함과 구분해 `증거 부족`으로 기록.

### 품질 루브릭

각 항목을 0~2점으로 채점한다. 총점 10점은 분석용이며 합격선을 대신하지 않는다.

| 항목 | 0: 사용 곤란 | 1: 수정 필요 | 2: 그대로 사용 가능 |
|---|---|---|---|
| 사실·근거 | 핵심 주장 오류 또는 판단 불가 | 일부 표현이 근거보다 강하거나 모호함 | 제품 주장이 근거와 맞고 창작 경계가 명확함 |
| 글·화면 일치 | 엉뚱한 화면·오류·로딩으로 핵심을 못 보여줌 | 관련 있지만 자르기·선택·순서 수정 필요 | 화면이 글의 핵심을 분명히 보여줌 |
| 독자 가치 | 무슨 쓸모인지 알 수 없음 | 의미는 있으나 설명이 추상적임 | 레고 이용자가 관심 가질 이유가 구체적임 |
| 페르소나·자연스러움 | 과장·내부 용어·부자연스러운 보고체 | 문장·농담·질문이 다소 억지스러움 | 자연스러운 반말, 취향과 유머가 과하지 않음 |
| 구체성·다양성 | 제품명만 바꾸면 쓸 수 있거나 최근 글을 사실상 반복 | 소재는 다르나 구성·마무리가 기계적으로 반복 | 레고/GoLe 맥락이 있고 최근 글과 구별됨 |

일일 홍보의 텍스트 전용 사례는 사전에 허용한 경우에만 화면 항목을 N/A로 둔다.
필수 이미지가 빠진 릴리스 초안은 N/A로 제외하지 않는다. N/A가 있으면 항목별 점수와
적용 항목 수를 보고하고 10점 만점 결과와 직접 비교하지 않는다.
450자·이모지 최대 1개 등 기존 톤 가이드 위반은 별도 체크하고 표현 수정에 반영한다.
질문·농담·이모지는 매 글 필수가 아니다. 창작 일화를 매번 넣는 것도 요구하지 않는다.

### 첫 검토 판정

- `그대로 사용`: 보류 조건 없고 원본 그대로 게시 가능한 품질.
- `경미한 수정`: 말투·길이·오탈자만 수정. 사실·핵심 메시지·이미지 교체는 여기에 포함하지 않음.
- `대폭 수정`: 핵심 설명 재작성, 사실 수정, 이미지 교체·재촬영이 필요.
- `사용 불가`: 소재나 결과를 폐기해야 함.
- `보류`: 중대한 결함 또는 증거 부족. 검토 후 위 네 판정으로 재분류하더라도 첫 판정은 보존.

이 판정은 실제 관리자의 승인 상태와 별개다. 평가가 좋아도 자동 승인하지 않는다.
이유 태그: `사실 오류 / 증거 부족 / 화면 부적합 / 정보 노출 / 홍보 가치 부족 / 말투 / 반복 / 형식 / 기타`.

## 집계 지표

분류·실행 버전별로 건수와 분모를 함께 보고한다. 분모 0은 0%가 아닌 N/A다.
아직 검토하지 않은 초안 수를 별도로 밝히고, 보류는 검토 완료 분모에 포함한다.

| 지표 | 산식·집계 방법 |
|---|---|
| 첫 검토 채택률 — 주 지표 | (그대로 사용 + 경미한 수정) / 첫 검토 완료 초안 |
| 중대한 결함률 | 확정된 보류 조건 결함이 있는 초안 / 첫 검토 완료 초안. 한 초안의 여러 결함은 1건으로 셈 |
| 증거 부족률 | 증거 부족으로 보류한 초안 / 첫 검토 완료 초안. 확정 결함률과 별도 표시 |
| 사실 수정 필요율 | 제품 사실 수정이 필요했던 초안 / 첫 검토 완료 초안 |
| 검토 부담 | 증거 확인을 포함한 실제 검토 시간과 수정 시간을 각각 기록하고 중앙값·최댓값 보고. 대기·휴식 제외 |
| 항목별 품질 | 루브릭 항목별 0/1/2점 건수. 평균 총점만으로 결함을 숨기지 않음 |
| 초안 확보율 | 평가 전에 사람이 생성 대상으로 정한 후보 중 초안을 제출한 수 / 생성 대상 후보 수 |
| 적절한 건너뛰기율 | 평가 전에 사람이 건너뛰기 대상으로 정한 후보 중 같은 판단으로 종료한 수 / 건너뛰기 대상 후보 수 |
| 기술적 실패율 | 모델·도구 오류 또는 한도 도달로 완료하지 못한 시도 / 실행 시도 수 |

실행 결과는 `submitted / intentional_skip / technical_failure / blocked_by_queue / no_candidate /
unknown_skip`으로 평가 기록에 구분한다.

**2026-09-20 갱신 — 전사를 뒤질 필요가 없어졌다.** 코드가 의도적 판단(`skipped`)과 턴 한도
도달(`deferred`)을 세션 `manifest.json` 의 `done` 필드에 따로 기록한다(D11). 매핑은 그대로
읽으면 된다 — `skipped → intentional_skip`, `deferred → technical_failure`(한도 도달),
`failed → technical_failure`(오류). `unknown_skip` 은 원장이 유실됐을 때만 쓴다.

**건너뛴 릴리스를 분모에 넣는다.** 주 지표인 첫 검토 채택률은 *만들어진 초안만* 세므로,
홍보할 만했는데 건너뛴 경우(거짓 음성)가 어디에도 잡히지 않는다. 실행마다
`skipped`·`deferred`·`failed` 건수를 함께 보고하고, 그중 사람이 "홍보했어야 했다"고 본 건수를
따로 센다.
큐 차단·후보 없음은 실행 실패율에서 제외하되 각각 건수를 공개한다. 후보 탐색의 누락도
확보율에서 드러나도록 사전 대상 목록과 실제 선택 목록을 대조한다.

비용은 실패·재시도를 포함한 전체 평가 비용 / 채택 가능한 초안 수로 보조 보고할 수 있다.
현재 모델 응답의 토큰 사용량을 평가용으로 저장하지 않으므로 비용 미수집은 N/A로 표시한다.
조회수·좋아요·유입·가입은 실제 발행 후 별도 성과 지표이며 v1 초안 품질 점수에 섞지 않는다.

## 최초 평가 절차와 사례 구성

1. 아래 유형으로 릴리스 사례 12개를 먼저 고정한다. 합성 사례는 합성임을 표시한다.
2. 모델 결과를 보기 전에 사람이 기대 행동과 확인 가능한 주장을 적는다.
3. 고정 입력으로 첫 결과를 수집한다. 실제 모델 평가와 스크립트 드라이런을 별도 집계한다.
4. 두 검토자가 처음 5개를 독립 채점하고 차이를 조정한다. 나머지는 한 명이 채점하되
   중대한 결함·모호한 창작 사례는 두 번째 검토자가 확인한다.
5. 첫 배치는 기준선이다. 채택률·시간의 합격 수치를 미리 사실처럼 정하지 않는다.
   결함이 있는 개별 글은 발행하지 않으며, 표본에서 결함 0건이어도 안전성이 증명됐다고 말하지 않는다.
6. 다음 버전은 같은 입력으로 비교하고, 추가 미공개 사례로 과적합 여부를 확인한다.

| ID | 사례 | 기대 행동·검토 초점 |
|---|---|---|
| R01 | 공개 화면에 확인 가능한 새 기능 | 생성, 기능과 사용자 가치의 일치 |
| R02 | 눈에 보이는 버그 수정 | 생성, 고친 범위를 과장하지 않음 |
| R03 | 내부 리팩터링만 있는 변경 | 의도적 건너뛰기 |
| R04 | 코드에는 있으나 화면에서 비활성인 기능 | 사용 가능하다고 홍보하지 않음; 보통 건너뛰기 |
| R05 | 현재와 다른 버전의 화면 | 확인 불가를 인지; 출시 사실 단정 금지 |
| R06 | 촬영에 이용자 식별 정보가 크게 노출 | 안전한 다른 화면 선택, 없으면 건너뛰기 |
| R07 | 최근 글과 같은 소재·화면 | 중복 홍보를 피하고 새 가치가 없으면 건너뛰기 |
| R08 | 이전 반려 사유가 포함된 이력 | 같은 결함 반복 여부 |
| R09 | 로딩 또는 오류 화면만 캡처 가능 | 정상 기능의 증거로 제출하지 않음 |
| R10 | 좋은 화면과 가벼운 개발 일화 | 창작 자체로 감점하지 않고 제품 사실과 분리 |
| R11 | 여러 변경이 섞인 릴리스 | 핵심 사용자 가치 선택, 내부 변경 나열 금지 |
| R12 | 도구 실패·턴 한도 도달 | 기술적 실패 분류, 의도적 건너뛰기와 구분 |

후속 일일 홍보 평가는 기존 기능 활용, 레고 취향 질문, 가벼운 농담, 반복 소재, 근거 없는
제품 주장 사례로 별도 구성한다. 매일 준비한다는 이유로 홍보 가치가 낮은 글을 강제로 채택하지 않는다.

## 실행 방법과 현재 한계

[건별 기록 양식](eval-record-template.md)을 복사해 배치별 평가를 기록한다.
현재 `--dry-run`은 배선·상태 흐름 확인용이며 실제 모델의 품질 평가가 아니다.
실제 모델 평가에는 유료 호출과 입력 전송 범위 확인이 필요하며 이번 문서 작업에서 실행하지 않는다.
운영 초안 등록도 평가에 필수는 아니다. 승인된 격리 환경 또는 보관된 초안을 사용한다.

성공한 실행은 체크포인트를 폐기하므로 전사가 항상 남아 있다고 가정하지 않는다.
근거·창작·토큰·검토 시간 수집과 `skipped` 사유 구분 자동화는 후속 계측 과제다.
현재 톤 프롬프트와 평가 기준은 역할이 다르다. 이번 변경은 런타임 프롬프트를 바꾸지 않는다.
