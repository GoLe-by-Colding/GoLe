# 설계

## 정보 구조

| 면 | 먼저 보여 줄 정보 | 주요 행동 |
| --- | --- | --- |
| 홈 | GoLe의 가치, 상품 탐색, 실제 공개 지표 | 상품 둘러보기 |
| 검색 | 검색어·적용 필터, 사진, 판매 가격, 구성·상태 | 조건 변경 → 상세 |
| 상세 | 사진 → 가격·상태 → 구성 고지 → 판매자 → 시세 근거 | 서버 준비 상태에 맞는 문의 또는 거래 |
| 판매 | 준비 조건, 작성 단계, 저장/실패 복구 | 조건 충족 후 등록 |
| 채팅 | 상품 맥락, 대화, 합의·완료 상태 | 해당 방으로 이동 |
| 내 정보 | 내 거래·컬렉션·계정·알림 | 목적별 관리 |

캐릭터는 헤더와 빈 상태에서 같은 원본을 쓴다. 모바일는 한 화면의 정보량을 제한하되
상품 카드는 가격/상태 비교에 필요한 밀도를 확보한다. 실사진은 그대로, 이미지 부재는 브릭 패턴이다.
색·버튼·타이포 정본은 기존 토큰이며 독립 테마나 새로운 컴포넌트 체계를 추가하지 않는다.

## 앱과 웹의 경계

- 앱 내부 링크는 정확한 웹 원점 검증을 통과해야 한다. 알림 경로는 검증한 path/query/hash를
  공통 WebScreen에 전달하고, 상세에서 복귀할 수 있는 네이티브 상단 동선을 둔다.
- 웹 인증은 HttpOnly 쿠키 기반이다. 토큰을 RN 저장소로 복사하지 않는다.
- 앱 탭 포커스와 웹 세션 재확인을 연결한다. URL의 탭 목적지와 선택된 RN 탭이 어긋나지 않게 한다.
- 앱 식별자는 표현 최적화에만 쓰며 권한·결제 허용 판단은 계속 서버가 담당한다.
- OAuth의 외부 브라우저 복귀, 실제 FCM 전달, 사진 권한은 별도 실행 증거가 있어야 완료로 표시한다.

### 알림과 복귀 동선

- 공개 서비스 경로만 허용하고 query/hash를 보존한다. 기존 RN 상세 주소는 유지하며,
  주문·부품·게시물처럼 전용 RN 화면이 없는 경로는 검증한 `web?path=` 화면에서 연다.
- 범용 알림 화면에는 네이티브 뒤로 가기를 제공한다. 앱 종료 상태에서 누른 알림은
  루트 내비게이션 준비 후 한 번만 처리하며 처리한 응답을 지워 재진입을 막는다.
- 탭 포커스·앱 활성화 시 웹의 기존 focus 구독에 신호만 전달한다. 쿠키나 계정 정보를
  RN으로 읽어 오지 않고, 새로고침으로 작성 중 입력을 지우지 않는다.

## 결제·정산 기획

실물 브릭 구매는 앱 안에서 PG 결제하는 방향이며 디지털 상품용 스토어 IAP로 설계하지 않는다.
판매자 정산은 기존 MANUAL 원장을 재사용한다. 수납 방식과 판매자 지급 방식은 별개로 결정한다.
코드상 MANUAL 지원이 PG 계약·C2C 판매자 지급 승인이나 운영 활성화를 대신하지 않는다.
자세한 계약/운영 조건과 공식 출처는 볼트의 `정산 모드와 단순결제 폴백`에 정리한다.

## 탭 ↔ 웹 목적지 동기화 (2026-10-09 구현)

탭마다 WebView가 하나라, 홈 탭 안에서 `/search`로 가면 선택된 탭(홈)과 화면(검색)이 어긋났다. 탭 뿌리는
`/`→홈, `/search`→검색, `/sell`→판매, `/chat`→채팅, `/profile(/…)`→내 정보다(앱 `views/web/model/navigation.ts`와
웹 `shared/lib/app-tab-link.ts`가 같은 표를 갖고, `app-tab.test.cjs`가 둘의 일치를 검사한다).

1. **웹 링크**(`app/(main)/app-tab-links.tsx`): 앱 안(`ReactNativeWebView` + 앱이 넣은 `__GOLE_APP_TAB__`)에서만, 다른 탭의 뿌리로
   가는 같은 원점 링크 클릭을 캡처 단계에서 막고 `{"type":"gole:navigate","path":"/…"}` 한 줄만 보낸다. 같은 탭 안 이동과
   상세·시세 같은 탭 밖 경로는 웹이 평소처럼 연다. 이전 앱 버전(브리지 없음)·앱 밖 브라우저에서는 꺼져 있다.
2. **앱 검증**(`appNavigationMessage`): 보낸 페이지가 정확히 신뢰 원점이고, 본문이 두 키 `{type, path}`뿐이며, 종류가 고정값이고,
   path가 알림과 같은 안전 경로 검사(`isSafeAppPath`)를 통과하고, 탭 뿌리일 때만 받는다. 명령·스크립트·토큰은 받지 않는다.
3. **전체 페이지 이동**: `onShouldStartLoadWithRequest`에서 다른 탭 뿌리로 가는 최상위 이동을 시작 전에 막고 그 탭으로 넘긴다.
4. **웹의 프로그램 이동**(`router.push("/")` 로그아웃·헤더 검색 등): 이미 바뀐 뒤라 `onNavigationStateChange`에서 그 탭으로 넘기고
   이 WebView를 한 단계 되돌린다(iOS 히스토리 shim·Android `doUpdateVisitedHistory`로 SPA 이동도 이벤트가 온다).
5. **받는 탭**: `router.navigate(탭, {to, at})`. 탭은 `to`를 다시 검증하고, 처음 열리는 탭이면 그 경로로 시작한다. 이미 열려 있으면
   현재 위치와 다를 때만 옮기되, 뿌리만 가리키는 요청(`/sell`)은 그 탭이 자기 영역에 있으면 옮기지 않아 작성 중인 폼을 지킨다.
   query·hash가 붙은 구체적 목적지(`/search?query=…`, `/chat?room=…`)는 지금 위치와 다를 때 옮긴다.
6. 탭이 아닌 화면(알림 상세 `web?path=`)은 탭 바가 없어 어긋날 일이 없으므로 1·2만 따른다.

## 앱 권한 문구 (2026-10-09 확인)

- 웹 사진 업로드(판매 글·커뮤니티·브릭 필터)는 `<input type="file" accept="image/…">`라 iOS WKWebView가 "사진 찍기"를 띄운다.
  `NSCameraUsageDescription`이 없으면 그 순간 앱이 종료되므로 `app.json` `ios.infoPlist`에 넣었다. 사진 보관함은 iOS 16.4+ PHPicker라
  권한 창이 없지만, 실제 용도와 같은 `NSPhotoLibraryUsageDescription`을 방어적으로 둔다.
- Android는 `react-native-webview`가 `CAMERA` 권한을 선언하지 않은 앱에서 카메라 앱 인텐트로 촬영하므로 권한 선언이 필요 없다.
- 실기기 확인(네이티브 빌드 후 촬영·선택)은 출시 조건으로 남긴다.

## 검수 후 수정 (2026-10-09, root 실관찰 기준)

### iOS 검색 입력 확대

- 원인: iOS WebKit은 글자가 16px보다 작은 입력란에 초점이 가면 화면을 확대하고, 입력을 마쳐도 되돌리지 않는다.
  공용 `Input`·`Select`는 이미 `text-base`(16px)였지만 검색은 `features/listing-filter`의 `SetAutocomplete`(`text-sm` 14px)를 쓴다.
  앱 WebView에서 그 입력을 누르면 약 1.15배 확대되어 메뉴·우측 검색 버튼·카드가 잘린 채 남았다(root 관찰).
- 같은 원인의 입력이 웹 전체에 18곳 있었다(검색 최소·최대가, 헤더 검색, 채팅 입력, 가격 제안, Q&A, 커뮤니티 검색 등).
  하나씩 고치면 새 입력에서 다시 생기므로 `app/globals.css`에 한 규칙을 둔다 — 손가락 포인터(`pointer: coarse`) 또는 sm 미만 폭에서
  `text-sm`·`text-xs`를 쓴 `input`·`select`·`textarea`만 16px로 올린다. 레이어 밖 규칙이라 utilities의 `text-sm`보다 우선한다.
  큰 글자 입력은 건드리지 않고, 넓은 데스크톱(정밀 포인터)은 그대로다. `maximum-scale`·`user-scalable=no`는 쓰지 않는다.
- 320px에서는 16px 검색창에 자리를 주려고 필터 버튼을 아이콘만 남기고 이름은 화면 낭독기용(`sr-only`)으로 둔다.

### WebScreen 수명주기

- **경로 인자 갱신**: 직전 구현이 `source`를 `useState(startPath)`의 첫 값으로 고정해, 탭이 아닌 화면(`web?path=`)이 경로 인자가
  바뀌어도 이전 페이지에 머물렀다. 이제 탭이 아닌 화면은 `path`를 따르고, 탭 화면만 첫 경로를 고정한다(다시 그려도 새로 고치지 않는다).
- **느린 로드 목적지**: 직전 구현은 목적지를 받자마자 `handledKey`를 소비하고 즉시 `injectJavaScript`로 옮겼다. WebView가 아직
  페이지를 다 불러오기 전이면 주입이 사라지고, 요청 키는 이미 처리됨으로 남아 목적지가 없어졌다. 이제 목적지를 `pending`에 두고
  WebView의 실제 `onLoad` 뒤에만 적용한다. 실패 화면(WebView가 내려감)·다시 시도(새 WebView) 사이에도 `pending`을 지키고, 로드 상태는
  새 WebView마다 처음부터 센다. 적용할 때 실제 현재 위치로 `shouldMoveTab`을 다시 판단해, 뿌리 요청이 작성 중인 폼을 지우지 않는 원칙과
  query·hash 보존·신뢰 원점 검증(`tabRequest`)은 그대로다.
- **두 번째 전체 로드 중 목적지**(root 코드 검토): 첫 `onLoad` 뒤에도 새 문서를 불러오는 중이면 주입이 사라질 수 있다. react-native-webview의
  이벤트 계약에 맞춰 로드 중을 따로 센다 — `onLoadStart`는 실제 문서 로드면 `loading=true`(iOS `didStartProvisionalNavigation`,
  Android `onPageStarted`)이고, Android의 SPA 주소 변화(`doUpdateVisitedHistory`)는 진행률 100이라 `loading=false`로 오므로 로드 중으로
  보지 않는다. 로드가 멈추면 `onLoad` 또는 진행률 1(`onLoadProgress`)에서 대기 목적지를 옮긴다. 이 화면이 다른 탭으로 넘기며 막은
  리다이렉트처럼 취소된 로드는 iOS가 -999 오류를 내지 않아 `onLoad`가 없지만 진행률 1로 끝난다. 끝 신호가 오지 않는 기기에서도 목적지는
  버려지지 않고 다음 `onLoad`까지 남는다.
- 회귀: `web-screen-lifecycle.test.cjs`가 실제 `web-screen.tsx`를 작은 훅 런타임으로 그려, 경로 갱신·로드 전 목적지·실패 후 다시 시도·
  폼 보존·메시지·전체 이동 차단·SPA 안전망·두 번째 로드 중 목적지·취소된 로드·Android SPA 주소 변화를 사건 순서대로 흘려 실제
  주입/이동을 확인한다(35건). 일부러 되돌린 세 변형(source 고정, 로드 전 즉시 주입, 로드 중 확인 없음)은 각각 "비탭 경로 갱신",
  "로드 전에는 주입하지 않는다", "새 문서를 불러오는 중에는 주입하지 않는다"에서 실패했다.

### 시세 E2E 날짜 의존 제거

- 원인: `prices.spec.ts`의 기간·차트 검사는 브라우저의 오늘을 기준으로 1개월·6개월 창을 계산하는데, 로컬 표본의 최신 미개봉 체결이
  2026-08-21이라 오늘(10-09) 기준 1개월 창이 비어 차트가 없었다. 날짜가 지나면 6개월 창도 같은 방식으로 빈다.
- 수정: 표본을 만들거나 DB를 바꾸지 않고, 화면과 같은 스냅샷 API를 읽어 "최신 체결 직전 1개월에 2건 이상"인 확정 시세 세트를 고른 뒤
  하이드레이션 이후 `page.clock.setFixedTime`으로 브라우저의 지금을 최신 체결 12시간 뒤로 고정한다. 1개월 창의 기대 건수는 화면과
  같은 `filterPricePointsByPeriod`로 계산해 차트와 "거래량 N건"을 정확히 비교한다. 빈 기간 계약은 지금을 최신 체결 62일 뒤로 고정해
  "1개월 체결 없음·이 기간에는 체결이 없어요"와 차트 없음을, 전체 창에서는 모든 체결 수를 확인한다. 차트 존재만 보는 다른 검사는
  날짜와 무관한 "전체" 창으로 본다. 조건에 맞는 세트가 없으면 건너뛰지 않고 이유를 밝혀 실패한다.

### 로그인 복귀 안내 문구

## PR #199 최종 리뷰 수정 (2026-10-09)

### 알림 상세에서 탭으로 갈 때 기존 탭 스택으로 복귀

- 결함(Codex 리뷰 P2): 탭이 아닌 화면(`web?path=` 알림 상세)은 루트 Stack에서 `(tabs)` 위에 쌓인다. 여기서
  `router.navigate({ pathname: "/sell", params })`를 부르면 Expo Router 57의 `stackRouterOverride`는 NAVIGATE가 현재 화면과
  이름이 다르고 `pop`이 없으면 아래 `(tabs)`를 찾지 않고 새 키로 `(tabs)`를 쌓는다 — `[기존 tabs, web, 새 tabs]`. 새 탭 상태라
  작성 중이던 판매 폼·검색 필터 대신 처음 화면이 열렸다.
- 수정: 비탭 화면만 `router.dismissTo(href)`를 쓴다. `dismissTo`는 POP_TO 액션이고, override는 POP_TO를 기본 StackRouter에 넘긴다.
  StackRouter는 현재 위치 아래에서 같은 이름의 `(tabs)`를 찾아 그 위를 걷어 내고, 그 route를 `{ ...route, params }`로 두어 키와
  중첩 `state`(탭 상태)를 유지한다. 탭 내비게이터는 바뀐 params의 `screen`·`params`를 받아 그 탭으로 navigate한다
  (react-navigation `useNavigationBuilder`). 탭 화면 안에서는 기존대로 `router.navigate`가 탭 내비게이터를 겨눈다.
- 근거는 설치된 코드의 실제 상태 전이다. `web-screen-lifecycle.test.cjs` 라우터 절은 앱의 실제 라우트 파일로 `getRoutes`·
  `getReactNavigationConfig`·`getStateFromPath`를 돌리고, `getNavigateAction`(push·navigate·dismissTo가 만드는 액션)을 StackClient의
  `StackRouter`(기본 + override)와 TabRouter에 그대로 적용한다. 화면 렌더러 모듈만 가짜로 꽂는다. 확인한 것:
  - push 뒤 `[(tabs), web]`이 되고, navigate는 `[(tabs), web, (tabs)]`로 리뷰의 재현과 같다.
  - dismissTo는 POP_TO로 `[(tabs)]`가 되며, 같은 키와 같은 중첩 상태 객체를 유지한다.
  - params `screen=sell`·`to=/sell?draft=1#top`(query·hash)이 전달되고, 판매·검색 탭의 키와 params가 그대로다.
  - 탭 안 navigate는 탭 내비게이터를 겨눈다.

### 목적지 로드 실패 뒤 다시 시도

- 결함(Codex 리뷰 P2): 직전 구현은 목적지를 주입하자마자 `pending`을 지웠다. 이미 열린 채팅 탭에 `/chat?room=r2`를 보내고 그 로드가
  네트워크 오류로 실패하면, 다시 시도가 고정된 첫 source(`/chat`)나 이전 방을 열었다. `targetKey`도 소비돼 r2를 잃었다.
- 수정: 대기 목적지를 `{ path, sentIn }`으로 두고 도착을 확인할 때까지 지우지 않는다.
  - `sentIn`은 주입한 문서 번호다(실제 문서 로드 시작마다 1씩 는다). 같은 문서에는 다시 보내지 않아 중복 주입·루프가 없다.
  - 목적지 주소에 닿았거나, 보낸 뒤 새 문서가 `onLoad`까지 끝났으면(웹이 로그인 등으로 다른 곳에 보낸 경우 포함) 끝난 것으로 본다.
    `onLoad`의 `nativeEvent.url`로 위치를 갱신한다. react-native-webview가 `onNavigationStateChange`를 `onLoad`보다 늦게 부르기 때문이다(`WebViewShared` `onLoadingFinish`).
  - 실패(`onError`, 보낸 목적지나 첫 화면의 5xx, 프로세스 종료)는 목적지를 지우지 않고 '보내지 않음'으로 되돌린다. 다시 시도는 새
    WebView의 source를 그 목적지로 열어 한 번에 간다(주입 없음).
  - 대기 목적지가 없으면 다시 시도는 실패한 위치를 연다. 뿌리만 가리키는 요청이 실패한 작성 위치(`/sell?step=2`)를 덮지 않는 폼 보존
    원칙은 다시 시도에도 같다.
  - 실패 화면에 있는 동안 온 새 요청은 이전 요청을 대신한다.
- 회귀: 컴포넌트 절 21개 시나리오와 라우터 절을 합쳐 61건이다. 보낸 목적지 실패→다시 시도, 주소 보고 전 실패(예비 탐색 실패),
  재실패, 새 요청 대체, 같은 문서 중복 주입 없음·도착 뒤 루프 없음, 목적지 5xx, 실패 뒤 뿌리 요청의 폼 보존을 담았다. 일부러 되돌린
  네 변형은 모두 해당 검사에서 실패했다.

  | 되돌린 변형 | 실패한 검사 |

- 매물 상세 제목 위 "#세트번호" 배지도 세트 페이지 링크다(접근 이름 "#번호 세트 페이지") — 휴대폰 첫 화면의 입구.
- 매물 상세의 시세 영역 제목 옆에 "세트 페이지 보기"(`/sets/번호`)를 둔다. 같은 세트의 다른 매물·구매 입찰·전체 체결 이력은 세트
  페이지에 모여 있는데 상세에서 그곳으로 가는 링크가 없었다.
- 미니피규어·부품·MOC 매물이 출처 세트 번호를 달았으면 제목을 "출처 세트 시세"로 바꾸고, 세트 시세를 "이 상품 상태 추정 시세"로
  강조하지 않는다. "세트 한 벌의 시세라 이 상품 가격과 바로 비교하지 않아요"를 밝힌다(판매가 비교 카드도 없다 — `priceComparableSetNumber`).
- 검증: 세트 매물 상세(e56c7143)를 Playwright 390px에서 확인(강조·링크·제목), search-and-listing·prices 14 통과. 미니피규어 매물은
  로컬·CI 시드에 없어 화면으로 보지 못했다(타입·코드 확인만).
