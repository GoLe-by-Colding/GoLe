# 정산 실행 모드 (settlement-mode)

## 왜 필요한가

상태기계는 `FUNDS_HELD → COMPLETED(정산 실행)`이라고 말하지만, "정산 실행"이 실제로
무엇인지 — 판매자 계좌로 **어떻게** 돈이 가는지 — 가 어느 문서에도 없었다.

플랫폼이 결제금을 보유했다가 지급하는 모델은 한국에서 전자금융거래법상
**결제대금예치업(에스크로업) 등록** 또는 PG의 에스크로·지급대행 계약을 전제한다.
개인 프로젝트가 즉시 확보할 수 있는 영역이 아니다. 이 전제가 검증되지 않은 채로
에스크로·정산 원장·수수료 정책이 얹혀 있었다.

이 문서의 법적 판단은 운영 가드의 보수적 기준이지 개별 사업에 대한 법률 자문이 아니다.
실제 개방 전에는 현재 C2C 구조와 개인 판매자 정산을 기준으로 PG·지급대행사와 전문가에게
서면 확인한다. 근거는 전자상거래법 제20조의 통신판매중개자 의무, 같은 법 시행령의
결제대금예치 제3자 요건, 전자금융거래법의 전자금융업 등록·정산자금 보호 규정이다.

이 스펙은 그 전제를 **명시적 선택**으로 바꾼다. 지급 계약이 없으면 플랫폼 결제 없이
당근형 직거래·채팅으로 서비스가 돌고, 계약이 생긴 뒤에만 결제·정산 단계를 연다.

## 결정

### D1. 안전 기본 모드는 DISABLED

`gole.settlement.mode` 로 선언한다. 기본값은 `DISABLED`다.

| 모드 | 돈의 흐름 | 자동 지급 | 요건 |
|---|---|---|---|
| `MANUAL` | 계약된 지급대행 절차를 운영자가 실행 → 구매확정 시 원장 `PENDING` 적재 → 외부 지급 확인 후 `PAID` | 안 함 | 현재 C2C 모델·개인 판매자 지급에 대한 PG/지급대행사의 서면 승인 + 법률·세무·운영 절차 확인 |
| `PROVIDER` | PG 지급대행이 판매자에게 직접 지급 | 함 | 지급대행 계약 + `SettlementExecutionPort` 구현체 |
| `DISABLED` **(현재·기본)** | 플랫폼 결제·지급을 모두 열지 않고 채팅 기반 직거래만 제공 | 안 함 | 없음 |

`MANUAL`은 법적·계약상 예외가 아니라 **지급 실행 주체만 운영자인 모드**다. PortOne 가입이나
테스트 결제 성공만으로 선택하면 안 된다. `gole.settlement.payout-contract-verified=true`는
현재 도메인·C2C 구조·판매자 유형에 대한 서면 승인을 실제로 확인한 뒤에만 설정한다.

`DISABLED`는 결제금을 플랫폼 계좌로 받은 뒤 수동 이체하는 "단순결제 폴백"이 아니다.
구매 버튼과 주문 생성 API를 닫고, 매물 당사자가 채팅에서 거래 조건을 정하는 Stage 1 이하의
안전 모드다. 계약 없는 B2 수동 정산안은 채택하지 않는다.

**모드는 설정만이 아니라 런타임 동작을 바꾼다.** `SettlementExecutor`가 부팅 시
모드와 구현체 조합을 검증한다 — `PROVIDER`인데 어댑터가 없거나, 비-`PROVIDER`인데
어댑터가 등록돼 있으면 **애플리케이션이 뜨지 않는다**. 계약 확인값이 꺼진 경우에는
서버 자체를 중단하지 않고 공개 단계를 Stage 1 이하로 영구 하향하며 모든 지급 실행을
잠근다. 운영 조회·복구 화면까지 함께 죽이면 오히려 사고 수습이 불가능하기 때문이다.

정식 운영 전환 목표는 `PROVIDER`다. 다만 지급대행 계약, 판매자 본인확인·계좌 등록,
실제 `SettlementExecutionPort` 구현을 모두 갖춘 뒤 Stage 3으로 전환한다.

**모드가 바뀌어도 체결가 기록은 동일하다.** 기록 트리거가 "정산 실행"이 아니라
"구매확정(`COMPLETED` 진입)"에 걸려 있기 때문이다. 시세는 이 제품의 해자이므로
정산 수단 변경에 영향받지 않아야 한다.

### D2. 지급 유예(payout holdback) = 3일

`gole.settlement.payout-holdback` 기본 `P3D`.

이체가 나간 뒤 분쟁이 열리면 플랫폼에는 판매자에게서 돈을 회수할 수단이 없다.
그래서 **분쟁 창구가 닫힌 뒤에 이체**되는 순서를 강제한다.

```
배송완료 ──P7D(auto-complete-after)──> 자동 구매확정 = 정산 원장 PENDING 적재
                                          └──P3D(payout-holdback)──> 지급 허용
```

`payout-holdback`은 `gole.pipeline.dispute-escalation-after`(3일)와 맞춘 값이다.
이 둘은 한 쌍으로 움직여야 하므로, 한쪽만 바꾸면 안 된다.

### D3. 수수료는 현행 유지(5%), 정책 변경은 설정으로

`FeePolicy`가 이미 요율을 설정으로 외부화하고 정산 결과에 적용 요율을 함께 보존한다
(과거 정산 재현 가능). MVP 무료화가 필요하면 `GOLE_FEE_RATE=0`으로 충분하며,
코드 변경은 필요 없다.

### D4. `COMPLETED`, `PAID`, `SETTLED`의 의미

- 주문 `COMPLETED`는 구매확정과 체결가 기록이 끝났다는 뜻이다. 판매자 계좌 지급 완료가 아니다.
- 정산 원장 `PAID`는 외부 증빙 번호와 함께 실제 판매자 지급을 확인한 최종 상태다.
- 기획 문서의 `SETTLED`는 현재 코드에서 정산 원장 `PAID`와 같은 뜻으로 사용한다. 주문 상태에
  별도 `SETTLED`를 추가하지 않는다. 주문과 정산의 생명주기를 한 상태기계에 섞으면
  `COMPLETED` 후 지급 실패·재조정 상태를 표현할 수 없기 때문이다.

## 요구사항

- [x] R1. 정산 실행 방식이 설정에 선언되고 **런타임 동작을 실제로 바꾼다**
      (`SettlementExecutor`가 모드별 자동 지급 여부를 가르고, 오설정은 부팅에서 거부).
- [x] R2. 구매확정 시 정산 원장에 `PENDING`으로 멱등 적재된다 (`SettlementPort.settleOnce`).
- [x] R3. 운영자가 외부 송금 증빙(은행 거래번호·배치 ID)과 함께 `PAID`로 표시할 수 있다.
- [x] R4. 지급 유예가 끝나기 전의 지급 시도는 `SETTLEMENT_HOLDBACK_ACTIVE`로 거부된다.
- [x] R5. 유예 위반 시 상태 전이를 시도조차 하지 않는다(원장 오염 방지).
- [x] R6. 정산 원장 조회는 지급 가능 시각(`payableAt`)을 함께 반환한다.
- [x] R7. 어드민 화면은 유예 중인 건의 지급 입력을 잠그고 지급 가능 시각을 안내한다.
- [x] R8. 판매자가 자기 정산 원장(지급 예정액·지급 가능 시각·지급 완료)을 조회할 수 있다
      (`GET /api/v1/orders/settlements`, 프로필 "판매 관리" 탭). 본인 것만 반환한다.
- [x] R9. 환불·분쟁으로 빠진 주문은 원장에 `PENDING`이 남아 있어도 지급이 거부된다
      (`SETTLEMENT_ORDER_NOT_COMPLETED`).
- [x] R10. 같은 주문의 원장 적재는 여러 번 호출돼도 한 행이다(`setOnInsert` 기반 upsert).
- [x] R11. `DISABLED`에서는 신규 플랫폼 결제·지급을 열지 않고 공개 단계를 Stage 1 이하로
      제한한다. 결제 없는 직거래·채팅은 계속 사용할 수 있다.
- [x] R12. `MANUAL`과 `PROVIDER`는 지급 계약 확인값이 없으면 Stage 2 이상과 모든 지급 실행이
      거부된다. 서버는 운영 조회·복구를 위해 부팅되지만 안전 클램프가 실행 단계를 Stage 1로
      영구 하향한다.
- [x] R13. 지급 작업은 운영자 또는 자동 실행기가 원장을 원자적으로 선점한 뒤에만 진행하며,
      지급 결과가 불명확한 건은 `PAYOUT_BLOCKED`로 격리해 외부 내역 확인 없이 재시도하지 않는다.
- [x] R14. 차단 건은 "외부 미지급 확인 후 재배정"과 "외부 지급됨 확인 후 증빙 기록"을
      별도 명령으로 처리한다. 지급됨 여부를 모른 채 `PENDING`으로 되돌릴 수 없다. 미지급을
      확인하면 `MANUAL`은 현재 운영자 작업으로, `PROVIDER`는 시도 예산을 새로 부여한 자동
      재시도 큐로 복구한다.
- [x] R15. 자동 지급기는 운영자 ID가 붙은 수동 지급 선점을 회수하거나 차단하지 않는다.
      모드 전환 중 사람이 이미 이체한 건을 자동 지급이 다시 집어가는 이중 지급을 막는다.
- [ ] R16. `PROVIDER` 어댑터 구현 — PG 지급대행 계약 후 착수. 포트는 이미 있다
      (`SettlementExecutionPort`). 구현체를 등록하고 `mode=PROVIDER`로 올리면 된다.
